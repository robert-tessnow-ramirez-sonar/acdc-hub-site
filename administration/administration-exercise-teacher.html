1

Understand the issue lifecycle, and how permission changes it

Difficulty 1/10Stretch

Goal: Know how an issue's status/resolution can change, and how the "Administer Issues" permission affects what you can do to it.

Model answer

The issue lifecycle runs through statuses like Open, Confirmed, Resolved (with a resolution: Fixed, Won't Fix, False Positive), and Reopened. Actions like Confirm, Resolve, Reopen, Won't Fix, and False Positive are all transitions between these states. The "Administer Issues" project permission gates the ability to change an issue's status/resolution and to assign it to someone; without it, a user can typically still comment and view issues but cannot change their state.

Grading notes

Pass: correctly separates "can view/comment" from "can change status/resolution," and names Administer Issues as the gating permission. Common miss: describing this as the same lifecycle as security hotspots (item 2), it isn't.

2

Understand the security hotspot lifecycle, and how permission changes it

Difficulty 1/10Stretch

Goal: Know how a security hotspot's status/resolution can change, and how the "Administer Security Hotspots" permission affects what you can do to it.

Model answer

Security hotspots use a review workflow distinct from the issue lifecycle: To Review, Acknowledged, Fixed, and Safe, framed around whether the hotspot needs a human security review rather than a bug/code-smell resolution. The "Administer Hotspots" permission (also called Administer Security Hotspots) gates changing a hotspot's review status; without it a user can typically view hotspots but not mark them Safe/Fixed/Acknowledged.

Grading notes

Pass: correctly names the review states (To Review, Acknowledged, Fixed, Safe) as distinct terminology from issue resolutions, and names Administer Hotspots as the gating permission. This is a common support confusion point, since hotspots look similar to issues in the UI but follow a different model.

3

Compare a Support Info File and a System Info File

Difficulty 1/10Core

Goal: Understand there are effectively two names for closely related content, and which detail is available on which edition.

Model answer

"System Info" is the product/documentation name for the feature under Administration > System, and the downloadable snapshot from the "Download System Info" button. "Support Info File" is the same downloadable artifact, referred to that way specifically in Sonar's support/ticketing context, when a support engineer asks a customer to attach it to a case. They are the same file under two names used by different audiences, not two separate exports. The System Info page/feature itself exists in Community Edition too; what's gated by edition or support contract is things like downloading raw log files from the UI, and richer licensing/line-of-code detail available on commercial editions.

Grading notes

Pass: correctly identifies these as the same artifact under two names (product-facing vs. support-facing), not two different files. Common miss: assuming "Support Info File" is an Enterprise-only superset, it's the same download; what differs by edition/contract is related but separate (log downloads, licensing detail).

4

Go through a System Info File and check the configurations

Difficulty 1/10Core

Goal: Understand what's actually inside a System Info snapshot.

Model answer

The System Info file is a JSON document with sections covering System (version, edition, uptime), Database (vendor, version, connection pool stats), Settings/Configuration (a large key-value dump of most instance settings, including housekeeping values and default Quality Gate info), installed plugins and their versions, and (on a cluster) per-node breakdowns. It's valuable to support because it answers most "what version/edition/config is this instance running" questions in one file, without a back-and-forth asking the customer to manually check and paste settings one at a time.

Grading notes

Pass: names at least 3 real sections (System, Database, Settings, Plugins) and can point to a specific setting they located, such as a housekeeping value or a Quality Gate default. Strong answer: explains the efficiency gain for support (one artifact vs. many follow-up questions).

5

Modify a Quality Profile by editing its backup XML file

Difficulty 1/10Stretch

Goal: Understand that a Quality Profile can be edited outside the UI by editing its exported backup.

Model answer

Exporting a Quality Profile via "Back up" produces an XML file listing every active rule and its parameters, plus profile metadata (name, language, parent profile if extended). Editing the XML to remove a block and change the name element, then restoring it, creates a new profile missing that rule under the new name. This technique is useful for bulk edits across many rules at once, cloning-with-tweaks without repeating UI clicks, and keeping a profile definition under version control outside the SonarQube database.

Grading notes

Pass: confirms they actually removed a rule and renamed it via XML edit, and can articulate at least one practical use case (bulk edit, cloning, version control) beyond "because it's possible."

Display a login message

Difficulty 1/10Stretch

Goal: Find the setting that lets an admin show a custom message on the login page.

Model answer

The login-page custom message is under Administration > General settings > General (sometimes labeled something like "Login message" or found under a Security/General subsection depending on version), and it renders on the login screen before authentication. A realistic use case: telling everyone hitting the login page about a scheduled maintenance window, an upcoming version upgrade, or where to find internal support contacts, before they even log in.

Grading notes

Pass: names the setting's approximate location and confirms it renders on the login page specifically (pre-auth), plus a plausible use case.

7

Display an announcement message

Difficulty 1/10Stretch

Goal: Find the setting that lets an admin show a banner/announcement to logged-in users.

Model answer

The announcement message is a separate setting from the login message, it targets users who are already logged in, typically shown as a banner across the top of the UI rather than on the login screen. This distinction matters for support: a customer asking "how do I message all my users" needs to know whether they mean pre-login visitors or already-authenticated users, since those are two different settings with two different audiences.

Grading notes

Pass: correctly distinguishes audience (pre-auth vs. logged-in) and placement (login screen vs. in-app banner) between this and item 6's login message. This distinction is the actual point of the exercise.

8

Segregate project configuration from project permissions

Difficulty 1/10Stretch

Goal: Understand where project-level configuration management is separated from project-level permission management.

Model answer

Project-level configuration (Quality Gate/Profile assignment, analysis parameters, webhooks, links) and project-level permissions (who has Browse, Administer Issues, Execute Analysis, etc.) are managed under separate sub-sections of a project's Administration tab. A project can have an "Administer" permission split from other admin-adjacent capabilities, letting an org grant someone rights to tune configuration without being able to grant themselves or others broader access. Real scenario: a build/tooling team might need to adjust a project's Quality Gate or webhook config regularly, but shouldn't be able to add themselves as a project owner or change who else has access.

Grading notes

Pass: correctly identifies configuration management and permission management as separate concerns/sections, and gives a plausible real-world reason to split them (least privilege, avoiding self-escalation).

9

Delegate Quality Profile and Quality Gate permissions to a group or user

Difficulty 1/10Stretch

Goal: Understand the use case for delegating QP/QG management without full instance admin rights.

Model answer

Quality Profiles and Quality Gates each support assigning specific "administrators" (a group or user) scoped to just that profile/gate, separate from global SonarQube Administrators. Granting this lets a delegated user or group edit that one Quality Profile or Gate without being made a full instance admin. Real reason: a large org might want each language or product team to own and tune their own Quality Gate/Profile without needing central IT/platform admins to be the bottleneck for every rule tweak.

Grading notes

Pass: confirms the delegated user could edit the specific QP/QG but nothing else instance-wide, and gives a scalable-organization rationale (avoiding a central-admin bottleneck) rather than just "because you can."

10

Download logs from the UI

Difficulty 1/10Core

Goal: Understand when and why to pull logs directly from the SonarQube UI instead of the filesystem.

Model answer

Logs can be downloaded directly from Administration > System, near the System Info download, typically covering web, Compute Engine (ce), Elasticsearch (es), and access logs. This UI path is most useful for support-contract customers who want a quick, self-service way to pull recent logs without shell/filesystem access to the server. It's less useful (or insufficient alone) on a clustered Data Center deployment, where logs are spread across multiple nodes and the UI download may only reflect a subset, so direct filesystem or centralized log aggregation access matters more there.

Grading notes

Pass: names the log types available (web/ce/es/access) and correctly notes the UI download's limitation on a multi-node Data Center cluster versus a single-node instance.

11

Create a custom Quality Profile, change a rule's severity, and fail an analysis

Difficulty 2/10Core

Goal: Know how to create and edit a Quality Profile end to end.

Model answer

Creating a Quality Profile (from scratch or copied), setting a rule's severity to Blocker, assigning the profile to a project, and analyzing code that triggers that rule causes the analysis to report a Blocker issue. Whether that alone fails the Quality Gate depends on the Gate's own conditions (e.g. "no new Blocker issues" or a rating-based condition), changing a rule's severity doesn't automatically fail anything; it's the separate Quality Gate configuration that turns a severity into a pass/fail outcome.

Grading notes

Pass: correctly identifies that severity change alone doesn't fail an analysis, it has to be connected through a Quality Gate condition that reacts to that severity/rating. This is the key insight the exercise is testing for.

12

Lock yourself out of a project's permissions, then fix it

Difficulty 2/10Stretch

Goal: Understand that it's possible to remove all access to a private project, and how a system admin restores it.

Model answer

Removing every permission grant on a private project (including your own) locks everyone, including project admins, out of managing it through the normal Permissions UI. A global/instance System Administrator can still restore access: from the global Administration > Security/Users area (or via the "Administer" system permission), a system admin can grant themselves or another user Administer permission on that specific project even though no project-level admin currently exists, then that person can re-assign the rest of the permissions normally.

Grading notes

Pass: confirms they actually reproduced the lockout and used a genuinely global/system-admin path (not a project-level workaround, since none exists once permissions are fully stripped) to restore access.

13

Find the first analysis date of every project using the Web API

Difficulty 2/10Stretch

Goal: Practice calling the SonarQube Web API directly, and know which permission is required.

Model answer

Using the Web API (documented at /web_api on the instance, or in official docs), an endpoint like api/project_analyses/search (or equivalent) returns a project's analysis history including timestamps; the earliest entry gives the first analysis date. This requires at minimum Browse permission on the project, and a valid token (project analysis token or user token) passed as the API credential; without sufficient permission the call returns a 403/permission error rather than data.

Grading notes

Pass: names a plausible analysis-history endpoint, correctly identifies Browse as the minimum permission needed, and reports what error they got when testing without it.

14

Stop live Portfolio calculation

Difficulty 2/10Stretch

Goal: Understand the setting that controls automatic Portfolio recomputation.

Model answer

The Portfolio recomputation-hours setting controls how frequently Portfolios automatically refresh their aggregated metrics. Setting it to a very large interval, or in some versions disabling the schedule, stops live recomputation, so a Portfolio's dashboard numbers stay frozen even as underlying project analyses continue. An admin might want this to reduce compute load on a large instance, control costs, or deliberately freeze a snapshot for a specific reporting period (e.g. a quarterly business review) without values shifting underneath them.

Grading notes

Pass: names the recomputation-hours setting and confirms observed behavior (dashboard stops updating), plus a plausible reason (load/cost control, or freezing a snapshot for reporting).

15

Configure global test exclusions and try to override them at the project level

Difficulty 2/10Core

Goal: Understand that the GLOBAL exclusion settings are a deliberate exception to normal settings inheritance.

Model answer

Global Test File Exclusions (and its sibling, Global Source File Exclusions) are explicitly documented as "forced global" parameters, an exception to SonarQube's normal settings inheritance where project-level settings override global ones. No project-level exclusion or scanner-side configuration can override or negate them, they must be changed at the global/UI level to take effect at all. This is the one class of setting purpose-built to be immune to project-level override.

Grading notes

Pass: correctly demonstrates the override attempt failed, and explains WHY: this specific setting is a documented exception to the usual global-then-project inheritance model, not a bug or a permissions issue.

16

Install and use a community plugin

Difficulty 2/10Stretch

Goal: Understand how third-party plugins are installed and what an admin needs to acknowledge before using one.

Model answer

Community plugins install either via the in-product Marketplace UI (where available) or by manually placing the plugin JAR into the extensions/plugins directory and restarting SonarQube. The most common real-world support issue is plugin incompatibility after a platform upgrade, a plugin built against an older SonarQube API breaking after an upgrade, since Sonar doesn't guarantee community plugin compatibility across versions. This means support should generally scope community plugin troubleshooting as "check compatibility with your version first," and be clear that third-party plugin bugs are outside Sonar's own support boundary.

Grading notes

Pass: names both install paths (Marketplace and manual JAR drop) and cites a real, plausible failure pattern (post-upgrade incompatibility) as the reason community plugins carry different support expectations than core features.

17

Export and import a project via the Web API or UI (project move)

Difficulty 2/10Stretch

Goal: Understand what does and doesn't come along when a project is moved this way.

Model answer

Exporting a project (via Web API or Administration UI) and importing it into a new project only carries branches/PRs that are marked to be kept when inactive; any inactive branch not explicitly flagged that way is excluded from the export, consistent with how housekeeping/dbcleaner would eventually purge that same branch anyway. In effect, export/import respects the same retention logic that housekeeping enforces, rather than being a full, unconditional snapshot of every branch that ever existed.

Grading notes

Pass: correctly connects the export/import behavior to the same retention logic as housekeeping (item 30), rather than treating it as an unrelated, separate quirk.

18

Create Portfolios: manually, by regex, and by setting computation hours

Difficulty 3/10Core

Goal: Study the different ways a Portfolio can be populated and scheduled.

Model answer

A Portfolio can be populated manually (adding specific projects one by one) or via a regex pattern that automatically matches project keys, with a new matching project picked up on the next recomputation without manual action. The Portfolio recomputation-hours setting controls how often either type refreshes; both eventually reflect the same underlying project data, the difference is purely in maintenance overhead, a regex-based Portfolio scales without ongoing manual upkeep as new matching projects appear, while a manual one requires someone to remember to add them.

Grading notes

Pass: built both a manual and regex-based Portfolio, and can articulate the maintenance-overhead tradeoff between them (manual = precise but requires upkeep, regex = automatic but only as good as the naming convention it relies on).

19

Create a portfolio with sub-portfolios and applications (multi-level structure)

Difficulty 3/10Core

Goal: Understand that Portfolios can be nested multiple levels deep, mixing sub-portfolios, Applications, and plain projects.

Model answer

A multi-level structure (top Portfolio containing sub-portfolios, which contain a mix of plain projects and Applications) correctly rolls metrics up from every level to the top, an Application's own aggregated metrics feed into its parent Portfolio just like a plain project's would. Applications aggregate their own child projects' code, so a project counted inside an Application is not separately double-counted again at the Portfolio level beyond what the Application already aggregated, the rollup is designed to avoid double-counting LOC/issues across that hierarchy.

Grading notes

Pass: successfully built at least a 2-level nested structure mixing sub-portfolios, an Application, and plain projects, and confirmed metrics rolled up correctly without obvious double-counting. If they found double-counting, that's worth flagging as a genuine edge case to verify against current docs rather than dismissing.

20

Create a user token, a project token, and a global token, then analyze with each

Difficulty 3/10Core

Goal: Know where each token type is created and what actually differs when you use it.

Model answer

User tokens are created from a user's own account (My Account > Security), and give that token all the permissions of the issuing user (a global admin's user token has full instance rights). Project analysis tokens are scoped to a single project and can typically be created by anyone with Execute Analysis permission on that project; a leaked project token only exposes that one project's analysis capability. Global/organization tokens (where available, e.g. on Cloud) can trigger multi-project actions but are still narrower in blast radius than a highly-privileged user's own token. The practical takeaway: prefer project-scoped tokens over broad user tokens wherever the workflow allows it, since a leaked project token limits the damage.

Grading notes

Pass: correctly ranks blast radius from broadest (a privileged user's user token) to narrowest (a project-scoped token), and can name roughly where each token type is created. This is a genuinely important security-hygiene answer for support to give customers.

21

Configure a project to notify you when its Quality Gate fails

Difficulty 3/10Stretch

Goal: Understand the notification mechanism end to end.

Model answer

Project notification preferences live under each user's own account settings, scoped per project (not a single global admin toggle), letting a user subscribe to events like "my Quality Gate status changes" for specific projects they care about. After subscribing and triggering a failing analysis, the default delivery channel is email; without additional integration configured (e.g. a webhook to Slack), email is the only channel available out of the box.

Grading notes

Pass: correctly locates notification preferences as a per-user, per-project setting (not instance-wide), confirms delivery via email, and knows email is the default/only built-in channel absent further integration (webhooks) work.

22

Download every kind of report available out of the box

Difficulty 3/10Core

Goal: Find out what reporting formats SonarQube ships without any add-on.

Model answer

PDF export is available on individual projects, Applications, and Portfolios directly from their dashboards. Security reports and any Regulatory report (e.g. OWASP/PCI DSS style compliance mappings) are typically project-level features and are gated to specific editions (commercial editions, not Community). The reports differ meaningfully in content, a PDF dashboard export is a snapshot of the visual dashboard, while security/regulatory reports map findings against specific compliance frameworks, they are not just re-skinned copies of the same data.

Grading notes

Pass: successfully found and downloaded PDF exports at multiple levels (project/Application/Portfolio) and identified Security/Regulatory reports as edition-gated and substantively different in content, not just different formatting of the same dashboard.

23

Configure SonarQube to be accessible without authentication

Difficulty 3/10Stretch

Goal: Realize this non-default, discouraged configuration exists, and understand why it's a bad idea.

Model answer

The setting that forces authentication (often called "Force user authentication") is on by default and can be turned off, at which point anonymous users can browse project data, issues, and potentially source code without logging in. The concrete risk: this exposes potentially sensitive source code, security findings, and configuration details to anyone who can reach the instance's URL, including public internet exposure if the instance isn't otherwise firewalled. Sonar's docs explicitly discourage this because most organizations underestimate how much sensitive detail is visible once authentication is bypassed.

Grading notes

Pass: names the "force authentication" setting and articulates a concrete risk (exposure of source code/security findings/config, not just a vague "it's insecure"). This should only ever be tested on a disposable instance, flag if the new joiner didn't note that caution themselves.

24

Create a conflict between analyzers using the same file suffix

Difficulty 3/10Stretch

Goal: Observe what happens when two language analyzers are both configured to claim the same file extension.

Model answer

Setting two analyzers' file-suffix configuration to both claim the same extension (e.g. .sql for both a T-SQL and a PL/SQL analyzer) causes analysis to behave unpredictably for files with that extension, commonly one analyzer silently "wins" and processes the file while the other ignores it, or the scanner logs a warning/error about an ambiguous language association. A support engineer should look in scanner logs for language-detection or file-association warnings mentioning the conflicting extension, that's the fingerprint of this exact misconfiguration.

Grading notes

Pass: actually reproduced a real conflict and can describe what appeared in scanner output (a warning, unexpected language attribution, or files being skipped), rather than only describing the setup without observing the failure.

25

Create a permission template and apply it to projects matching a regex

Difficulty 4/10Core

Goal: Understand how Permission Templates automatically apply to matching projects.

Model answer

A Permission Template lets an admin pre-define a set of permission grants (users/groups mapped to specific permissions) plus a project-key regex pattern; any project whose key matches that pattern automatically receives those grants, without manual per-project assignment. Renaming or creating a project so its key matches the pattern applies the template's permissions immediately (or on next relevant trigger, depending on version); a non-matching project is unaffected and keeps whatever default/manual permissions it already had.

Grading notes

Pass: confirmed a matching project received the template's permissions automatically, and separately confirmed a non-matching project did NOT, that negative test is what proves the regex-matching behavior rather than a coincidental default permission.

26

Force the change of the Server ID

Difficulty 4/10Core

Goal: Understand exactly what triggers a Server ID change.

Model answer

The Server ID is derived from the database connection configuration (e.g. sonar.jdbc.url) combined with a value generated the first time the database was set up; changing the database connection string (switching a hostname to an IP even pointing at the same machine, or pointing at a different/fresh database) regenerates the Server ID. The real-world consequence: a changed Server ID invalidates the existing license, since commercial licenses are tied to a specific Server ID, requiring a new license to be issued. This makes Server ID changes a real risk during database migrations, DR failover, or any change to the JDBC connection string, even ones that don't change the actual data.

Grading notes

Pass: correctly identifies the DB connection string (not the application server itself) as the actual trigger, and names license invalidation as the concrete consequence. Common miss: assuming moving/upgrading the application server itself changes the Server ID, it doesn't, as long as the DB connection details are unchanged.

27

"Cheat" a New Code Quality Gate by adjusting the New Code definition

Difficulty 4/10Stretch

Goal: Understand exactly how the New Code definition drives Quality Gate evaluation, by deliberately gaming it.

Model answer

Setting a project's New Code definition to a number of days shorter than how long ago a real Bug issue was introduced moves that issue outside the "new code" window the Quality Gate evaluates, so a Gate condition like "no new Bugs" no longer sees it and the Gate passes despite a real, known issue existing in the codebase. This is a genuine risk support should be aware of: a team could accidentally (through a misconfigured New Code period) or deliberately (to make a report look better) hide real problems from Quality Gate evaluation without actually fixing anything.

Grading notes

Pass: actually reproduced the specific scenario (issue N days old, New Code window set to fewer than N days, Gate passes) and can articulate the risk in terms support would care about: a customer's Gate looking healthy while a known issue is invisible to it.

Create a custom Quality Profile in a previous LTS and upgrade to the next LTS

Difficulty 5/10Stretch

Goal: Observe the real impact an LTS upgrade can have on a custom Quality Profile.

Model answer

Creating a custom Quality Profile in an older LTS, then upgrading to the next LTS, can change the profile's effective behavior even though no one edited it: rules can be deprecated, renamed, have default parameters changed, or be replaced by newer equivalents in a given LTS release. The correct way to assess impact is to diff the profile's rule set against that LTS's release notes for rule changes, rather than assuming a profile is frozen in time just because nobody touched it in the UI.

Grading notes

Pass: correctly frames the risk as coming from Sonar's own rule changes during an upgrade (not from any action the customer took), and describes checking release notes as the way to anticipate or explain differences, rather than only reporting whatever they happened to observe in one test.

29

Configure Housekeeping so specific branches are ensured to be purged

Difficulty 5/10Core

Goal: Understand sonar.projectDate and sonar.dbcleaner.daysBeforeDeletingInactiveBranchesAndPRs well enough to force a specific cleanup outcome.

Model answer

sonar.projectDate lets an analysis be submitted with a backdated timestamp, useful for importing historical data or, in this exercise, simulating that a branch's last analysis happened further in the past than it really did. daysBeforeDeletingInactiveBranchesAndPRs controls how many days of inactivity make a branch/PR eligible for automatic purging; setting it to 0 means effectively all non-exempt branches (any branch not explicitly marked "keep when inactive") are purged on the next housekeeping run, with no grace period. This setting can only be tuned in days/weeks, it cannot be fully disabled to "never purge."

Grading notes

Pass: correctly used sonar.projectDate to simulate branch age, confirmed the 0-day setting purges non-exempt branches essentially immediately, and correctly notes the setting can't be turned off entirely, only tuned numerically.

30

Create a custom Quality Gate that fails on any critical issue, on top of the default conditions

Difficulty 6/10Core

Goal: Understand how custom Quality Gates are built without accidentally dropping the built-in protections.

Model answer

The default Quality Gate ('Sonar way') includes conditions like new/overall reliability, security, and maintainability ratings, and coverage/duplication thresholds on new code (exact condition set varies by version). Building a custom Gate that copies every one of those conditions and adds a new one (Critical issues > 0, or the closest current equivalent severity/rating condition) and then reproducing a Critical issue on a test project confirms the Gate fails specifically because of the new condition, not because one of the inherited default conditions also happened to fail. Isolating which condition triggered the failure (visible on the Quality Gate detail for that analysis) is the key verification step.

Grading notes

Pass: actually listed the default Gate's real conditions (not a guess), built a Gate that includes all of them plus the new one, and specifically confirmed via the Gate failure detail that the NEW condition (not a coincidental default-condition failure) caused the fail.

31

Identify the different ways to calculate licensed lines of code (ncloc) for an instance

Difficulty 6/10Stretch

Goal: Become familiar with multiple methods of getting the same underlying number, and know when each is appropriate.

Model answer

There are at least three ways to get licensed ncloc: (1) a Web API call against a license-usage or measures endpoint that returns ncloc per project or instance-wide, (2) community-published scripts (for those without a commercial license/API access) that sum ncloc from logs or other Community-accessible data, and (3) a direct SQL query against the database's project measures tables, useful when API/UI access is unavailable or when cross-referencing at scale. Critically, ncloc for licensing purposes counts only the largest branch or PR per project (not necessarily the main branch), and excludes test code, unsupported-language code, comments/blank lines, and Application-level aggregation (to avoid double-counting the underlying projects).

Grading notes

Pass: named all three method categories (API, script, SQL) and correctly stated the "largest branch, not necessarily main" rule plus at least one exclusion category (test code, unsupported language, or Application double-counting avoidance). This rule is frequently the source of "why is my LOC count different from what I expected" tickets.

32

SMTP configuration and notifications

Difficulty 6/10Stretch

Goal: Learn the full notification pipeline, from SMTP server configuration through to a user actually receiving an email.

Model answer

SMTP settings (server, port, authentication, from-address) live under Administration > General > general/email settings; pointing them at a real or test SMTP relay (a local catcher like MailHog works well for testing without spamming real inboxes) enables outbound email. Triggering a subscribed notification (e.g. a Quality Gate failure from item 21) should then produce a real email at the configured relay. If it doesn't arrive, the troubleshooting order should be: confirm SMTP settings are saved and correct (test connection if that option exists), confirm the specific user actually has an active notification subscription for that project/event, and only then suspect something else (spam filtering, network/firewall blocking outbound SMTP).

Grading notes

Pass: actually configured SMTP against a real or test mail catcher and confirmed (or attempted and diagnosed) delivery, and gives a sensible troubleshooting order (SMTP config, then subscription, then everything else) rather than a random guess list.
