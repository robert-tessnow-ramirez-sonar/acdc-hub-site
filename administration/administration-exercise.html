Understand the issue lifecycle, and how permission changes it

Difficulty 1/10Stretch

Goal: Know how an issue's status/resolution can change, and how the "Administer Issues" permission affects what you can do to it.

Where to look, not what to write
  • Open a project's Issues page and look at what actions are available on an open issue (Confirm, Resolve, Reopen, Won't Fix, False Positive, etc.). Note the full set of transitions.
  • Try the same actions as a user who does NOT have the project's "Administer Issues" permission, versus one who does. What changes, and which specific transitions require that permission?
  • Write down the issue lifecycle as a simple state diagram in your own words: what states exist, and which transitions are permission-gated.

Compare a Support Info File and a System Info File

Difficulty 1/10Core

Goal: Understand there are effectively two names for closely related content, and which detail is available on which edition.

Where to look, not what to write
  • Go to Administration > System in a SonarQube instance and find the "Download System Info" button. Download it and open the resulting file.
  • Search Sonar's own support-facing documentation and community posts for the phrase "Support Info File" and see how it's used relative to "System Info." Are these actually two different downloadable artifacts, or the same one referred to differently by different audiences?
  • Identify which pieces of information on that System Info page (or actions available from it, like raw log downloads) depend on having a commercial support contract or a specific edition, versus what's available in Community.

Where to look, not what to write

"Cheat" a New Code Quality Gate by adjusting the New Code definition

Difficulty 4/10Stretch

Goal: Understand exactly how the New Code definition drives Quality Gate evaluation, by deliberately gaming it.

Where to look, not what to write
  • Introduce a Bug-severity issue into a test project and analyze it so it's flagged, then note how many days ago that issue was introduced.
  • Set the project's New Code definition to "number of days," using a day count SHORTER than how long ago the issue was introduced (e.g. issue is 5 days old, set New Code to 4 days).
  • Re-analyze and confirm the Quality Gate now passes, since the issue no longer falls inside the New Code window. Explain in your own words why this is a genuine risk for support to be aware of, teams could accidentally (or deliberately) misconfigure this to hide real problems.

Identify the different ways to calculate licensed lines of code (ncloc) for an instance

Difficulty 6/10Stretch

Goal: Become familiar with multiple methods of getting the same underlying number, and know when each is appropriate.

Where to look, not what to write
  • Method 1: use the relevant Web API endpoint for license usage / measures (ncloc) and call it for a project or the whole instance.
  • Method 2: if you have Community Edition access, look for scripts the community has published to sum ncloc across projects directly from logs or the API.
  • Method 3: if you have database access, write a SQL query against the appropriate table(s) that stores ncloc per project/branch. Compare all three methods on the same test instance, and note the rule about which branch's LOC counts (hint: it's not always the main branch).

SMTP configuration and notifications

Goal: Learn the full notification pipeline, from SMTP server configuration through to a user actually receiving an email.

Where to look, not what to write
  • Find the SMTP configuration settings under Administration > General (server, port, auth, from-address).
