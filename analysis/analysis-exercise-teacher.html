Scan a JS/TS project with and without sonar-project.properties

Difficulty 1/10Core

Goal: Understand basic analysis of a small project and what's actually required for JS/TS analysis to work at all.

Model answer

Without a sonar-project.properties file, a scan still works if all required parameters (project key, sources) are passed on the command line; the file just provides a persistent, checked-in place to store those settings instead of retyping them every time. For JS/TS specifically, very little is strictly required beyond a project key and source location, JS/TS analysis doesn't need a build step or compiled artifacts the way Java does.

Grading notes

3

Create a git repository and scan it

Difficulty 1/10Core

Goal: Understand git add/commit/checkout, and notice exactly how commit authorship and dates flow into SonarQube.

Model answer

Commit author and date come from git metadata at commit time (git config user.name/user.email, and the commit's authored/committed date) and are picked up by SonarQube's SCM integration during analysis, they drive issue auto-assignment (attributing an issue to whoever's commit introduced it) and backdating (deciding when an issue was actually introduced, for New Code calculations), rather than being tied to who ran the scan.

Grading notes

Pass: varied a commit's author/date and observed the corresponding change in SonarQube's blame/assignment data, confirming it's genuinely git-metadata-driven rather than scan-time-driven.

Create a local git branch and scan it in SonarQube

Model answer

Branch analysis requires passing a branch-name parameter (so the scan lands as its own branch entity in SonarQube instead of overwriting main), and the resulting branch appears with its own independent analysis history, issues, and Quality Gate status, separate from the branch it was created from.

5

Scan a branch with changes as a Pull Request from the command line

Difficulty 2/10Core

Goal: Understand how PR analysis is triggered purely from scanner parameters, without any CI/DevOps platform integration.

Model answer

PR analysis is triggered by passing PR-specific parameters directly (PR key, source branch, target/base branch) rather than a plain branch name, entirely from the command line with no CI or DevOps platform involved. The result is scoped differently from branch analysis: only issues introduced by the changeset (relative to the target branch) are reported, intended to feed a merge-gating Quality Gate rather than represent the full state of a long-lived branch.

Grading notes

Pass: named the correct PR-specific parameters (not branch parameters) and correctly describes the changeset-scoped reporting behavior as the key difference from branch analysis.

Run an analysis that includes only one specific file

Difficulty 2/10Core

Goal: Understand the inclusion and exclusion pattern mechanism.

Model answer

sonar.inclusions (or the equivalent narrowing exclusion pattern) set to match only the target file scopes the entire analysis down to that file; everything else in the project is skipped, and the UI shows metrics/issues only for that one file. This demonstrates that inclusion/exclusion patterns operate at the file-discovery stage, before any language-specific analysis runs.

Grading notes

8

Configure Global Exclusions and confirm they override project-level inclusions

Difficulty 2/10Core

Goal: Understand that Global Exclusions are a forced setting that cannot be overridden at the project level, even by an explicit inclusion.

Model answer

Global Exclusions (and Global Test File Exclusions) are documented as "forced global" parameters, they apply to every project instance-wide and cannot be overridden by any project-level setting, including an explicit project-level inclusion attempting to bring the file back in. This is an intentional, documented exception to SonarQube's normal settings hierarchy, where project-level settings otherwise generally win over global ones; it also can't be set via a config file, only through the UI.

Grading notes

Pass: actually attempted the override and confirmed it failed, and correctly identifies this as a deliberate, documented exception rather than a bug or a settings-precedence mistake on their part.

Obtain analysis parameters set for a scan via Scanner Context

Difficulty 2/10Core

Goal: Get familiar with the SonarQube UI well enough to locate the Scanner Context for a specific analysis.

Model answer

Scanner Context is found on a specific analysis's background task entry (via an action menu, "Show Scanner Context" or "Show SonarScanner Context" depending on version) and shows the actual parameters that run used. It is not populated if the analysis report itself failed to process, only successful analyses have a queryable context this way.

10

Understand the precedence of analysis parameters across levels

Difficulty 2/10Core

Goal: Know exactly which setting wins when the same parameter is set at multiple levels.

Model answer

General precedence, highest wins: command line / scanner arguments, then the scanner config file (sonar-project.properties), then project-level UI settings, then global-level UI settings. A key nuance: only values set through the UI are persisted to the database; anything set via command line or config file only applies to that specific analysis run and isn't "remembered" as the project's configured setting afterward.

Grading notes

Pass: determined the precedence experimentally (not just recited it), and separately notes the UI-persistence nuance, that only UI-set values show up as the project's stored configuration afterward.

11

Use sonar.scanner.internal.dumpToFile to capture analysis parameters

Difficulty 2/10Core

Goal: Understand how this debugging parameter dumps the full, actual list of properties a scan is using.

Model answer

sonar.scanner.internal.dumpToFile writes the scanner's full resolved property list (explicit and implicit) to a file at the given path, useful for debugging exactly what a scan actually used, similar in purpose to the Scanner Context UI view but generated client-side at scan time rather than pulled from the server afterward. Note: an older, deprecated sonar.scanner.dumpToFile (without .internal.) exists too, the .internal. variant is the current one to use.

Grading notes

Pass: actually inspected a real dump file and correctly notes the deprecated non-.internal. variant as an older name for essentially the same debugging mechanism.

12

Scan a Maven project from the command line

Difficulty 2/10Core

Goal: Get familiar with pom.xml, experiment with parameter precedence, and understand project key overrides and sonar-maven-plugin version pinning.

Model answer

The Maven scanner plugin (invoked via mvn sonar:sonar) runs inside Maven's own build lifecycle and reads the project model (pom.xml) directly, so it automatically fills in parameters like compiled classes location, dependency classpath, and source/target Java version. Overriding the generated project key is possible via a scanner property; pinning a specific sonar-maven-plugin version is done the normal Maven way, an explicit in the plugin declaration, to avoid silently picking up a newer plugin release.

Grading notes

Pass: actually tried a project key override and a version pin, and can describe what the plugin auto-populates from pom.xml that a generic scan wouldn't know about.

13

Analyze a Maven project without building it first

Difficulty 2/10Core

Goal: Understand the impact of missing compiled bytecode on Java analysis accuracy.

Model answer

For a Java project with more than a trivial single file, missing compiled bytecode causes analysis to either fail outright (with an explicit error pointing at sonar.java.binaries) or proceed in a visibly degraded mode with class-not-accessible warnings, depending on whether bytecode is fully or partially absent. Either way, type resolution, cross-class semantic analysis, and dataflow-based bug/vulnerability detection all suffer, since they depend on knowing real types and method signatures, not just parsing syntax.

Grading notes

Pass: actually compared issue output between an unbuilt and a properly built scan, and correctly attributes the difference to type-resolution-dependent rules specifically, not a vague "fewer issues happened."

14

Pass sonar.sources=. to a Maven analysis

Difficulty 2/10Core

Goal: Understand that Maven analysis always has a module hierarchy, even in a seemingly single-module project, and why overriding sonar.sources breaks that assumption.

Model answer

Maven analysis always has an implicit module hierarchy driven by each module's own pom.xml and standard directory layout; forcing sonar.sources=. at the root flattens that hierarchy, causing the scanner to recursively treat everything from the root as one flat source set. In a multi-module project this leads to duplicate analysis, issues attributed to the wrong module, and inclusion of files that shouldn't be scanned at all (build output, sibling module files).

Grading notes

Pass: actually reproduced the breakage on a multi-module project (a single-module project may not show an obvious problem) and can describe at least one concrete symptom (duplication, wrong attribution, or unwanted file inclusion).

15

Reproduce a scanner out-of-memory issue in Maven analysis

Difficulty 2/10Core

Goal: Determine why an analysis fails due to insufficient memory, and know how to allocate more to the right process.

Model answer

The affected process is the scanner's own JVM (the process running the analysis, invoked by Maven), not the SonarQube server. For scanner version 6.0+, memory is increased via the SONAR_SCANNER_JAVA_OPTS environment variable (e.g. -Xmx2048m); older scanner versions use SONAR_SCANNER_OPTS. This is a genuinely common point of confusion: MAVEN_OPTS governs the Maven build process itself, and sonar.ce.javaOpts governs the server's Compute Engine, neither of those fixes a scanner-side OOM.

Grading notes

Pass: correctly identifies the scanner process (not the server, and not plain Maven) as what needed more memory, and names the correct environment variable for their scanner version. This exact confusion (MAVEN_OPTS vs SONAR_SCANNER_OPTS vs sonar.ce.javaOpts) is a real, recurring support pattern.

17

Scan a single-module Maven Java project with coverage

Difficulty 3/10Core

Goal: Understand how to generate coverage and import it into a single-module Maven project's analysis.

Model answer

The general mechanism for all Java coverage import is: a coverage tool (JaCoCo) generates an XML report during the build, and sonar.coverage.jacoco.xmlReportPaths points the scanner at that file. Binary .exec-format JaCoCo reports are deprecated in favor of XML. For a single-module Maven project this is typically produced under target/site/jacoco/jacoco.xml via the jacoco:prepare-agent and jacoco:report goals.

Grading notes

19

Scan a multi-module Maven Java project with coverage

Difficulty 3/10Core

Goal: Understand coverage aggregation across multiple Maven modules.

Model answer

Multi-module Maven coverage requires an aggregated report, since JaCoCo by default only attributes coverage to the "current" module being built, undercounting any cross-module test coverage. The common approach is a dedicated report-aggregate module that produces a combined report (commonly at target/site/jacoco-aggregate/jacoco.xml) which the scanner is then pointed at, rather than pointing at each module's individual, incomplete report.

Scan a VB6 (Visual Basic) project and resolve a language/extension conflict

Difficulty 3/10Stretch

Goal: Understand how the scanner detects language by file extension, and how extension conflicts can happen and be resolved.

Model answer

The scanner determines a file's language from its extension, mapped via language-specific file-suffix settings configurable at both global and project level. A conflict arises when two different language analyzers are both configured to claim the same extension (for example .vb potentially ambiguous in some setups); resolving it means adjusting one analyzer's configured suffix list so the extension maps unambiguously to the intended language.

Scan a project using the sonar-scanner-cli Docker image

Model answer

Running the scanner via its official Docker image requires mounting the project source directory into the container (typically to /usr/src) and passing the SonarQube URL/token as environment variables or scanner arguments, rather than relying on a locally-installed scanner binary. 23

Analyze with the wrong token type and observe the failure

Difficulty 3/10Core

Goal: Understand the different token types (global/user/project) and what actually breaks when the wrong one is used.

Model answer

There are three token types: user tokens (inherit the full permission set of the issuing user), project analysis tokens (scoped to run analysis on one specific project only), and global analysis tokens (can run analysis across multiple projects). Using a token that lacks Execute Analysis rights on the target project (or one that's the wrong type for the context, e.g. an analysis token where a user token is required) produces an authentication or authorization error, typically a 401 for an invalid/unrecognized token or a 403 ("Insufficient privileges"/similar) for a valid but under-permissioned one.

Grading notes

Pass: actually captured a real error message from a deliberately-wrong token and can correctly categorize which of the three token types they used and why it failed.

24

Scan a JS/TS project with coverage

Difficulty 4/10Stretch

Goal: Understand how to generate coverage and import it for a JavaScript/TypeScript project.

Model answer

The mechanism is the same as Java coverage: a JS/TS test runner (commonly Jest, or Istanbul/nyc-based tooling) produces an LCOV-format report, and sonar.javascript.lcov.reportPaths (the unified property covering both JS and TS; the older separate TypeScript-specific property is deprecated) points the scanner at it. A real gotcha worth knowing: in a monorepo, if multiple workspaces produce coverage reports with identical relative file paths, coverage can collide and silently show as 0% for affected files unless the scan is run from a path that keeps them unique.

Grading notes

Pass: confirmed a real LCOV report imported correctly, and bonus points for surfacing the monorepo path-collision gotcha if they hit or researched it.

25

Analyze a repo cloned as a shallow clone

Difficulty 4/10Core

Goal: Understand the impact of a shallow git clone on analysis, particularly blame information and New Code detection.

Model answer

A shallow clone (git clone --depth 1) causes the scanner to log an explicit warning that blame information will be skipped; running git fetch --unshallow converts it to a full clone and blame/authorship data becomes available again on the next scan. Full clone depth matters beyond just blame: it also affects New Code detection accuracy and the ability to find a common commit ancestor for PR analysis on long-lived branches.

Grading notes

Pass: actually reproduced the warning on a shallow clone and confirmed the difference after converting to a full clone via git fetch --unshallow, not just read about the behavior.

27

Configure a database connection for PL/SQL analysis

Difficulty 5/10Stretch

Goal: See that some PL/SQL rules only raise issues when a data dictionary (live DB connection) is provided during analysis.

Model answer

PL/SQL's data dictionary feature lets the analyzer resolve schema objects (tables, views, synonyms) that aren't explicitly prefixed in the code, by querying a live Oracle database via a configured JDBC connection (URL and user); sonar.plsql.defaultSchema controls which schema unprefixed references are assumed to belong to. Certain rules can only fire with this schema-aware access, so the same code can show more issues with the DB connection configured than without it, this is intentional, not a bug.

Grading notes

Pass: actually compared issue counts with and without a real DB connection configured, and correctly frames the difference as intentional schema-aware rule behavior rather than a defect.

Get a taste of "New Issues on Old Code" caused by missing bytecode

Difficulty 5/10Core

Goal: Understand how missing bytecode can cause SonarQube to falsely flag unchanged code as containing new issues.

Model answer

There's a documented corner case where new issues can be detected on code outside the current New Code period; missing or incomplete bytecode is a plausible contributing cause, since degraded type resolution can change how or when certain rules fire on a given analysis, causing an issue that should have existed all along to instead compute for the first time on a later run and get miscategorized as new. This causal link (bytecode gap specifically causing this) is inference connecting two separately documented facts, not a single official statement, worth flagging as understood-but-not-officially-confirmed if asked to justify it further.

Grading notes

33

Simulate analyzing a project out of chronological order with sonar.projectDate

Difficulty 10/10Stretch

Goal: Understand the constraint that SonarQube can only "rebuild the past" in chronological order, and what breaks if you violate it.

Model answer

SonarQube enforces that analysis reports must be submitted in strictly chronological order for a given project/branch; using sonar.projectDate to submit an analysis dated earlier than the most recently stored analysis triggers a hard validation failure (an explicit error that the date cannot be older than the last known analysis), not a silent acceptance or soft warning. There's also a genuine, less-precisely-documented gap: there's no built-in API to simply list every background task's history/timestamps to help spot this kind of ordering problem after the fact, you'd have to reconstruct it by querying individual tasks via api/ce/task?id=....

Grading notes

Pass: actually reproduced the validation failure by submitting an out-of-order analysis, and separately notes the missing "list all background tasks" API as a real, current limitation rather than assuming a workaround exists.
