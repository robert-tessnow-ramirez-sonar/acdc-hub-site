Understand the precedence of analysis parameters across levels

Difficulty 2/10Core

Goal: Know exactly which setting wins when the same parameter is set at multiple levels.

Where to look, not what to write
  • Set sonar.inclusions to different, conflicting values at each of: the command line, sonar-project.properties, the project-level UI setting, and the global-level UI setting.
  • Run the analysis and determine experimentally which value actually took effect, rather than assuming a precedence order from memory.
  • Note explicitly: settings applied only via command line or file are not stored in the database, only UI-set values persist there, which matters when you're trying to see what's "configured" for a project versus what was passed for one specific run.

Reproduce a scanner out-of-memory issue in Maven analysis

Difficulty 2/10Core

Goal: Determine why an analysis fails due to insufficient memory, and know how to allocate more to the right process.

Where to look, not what to write
  • Deliberately constrain the memory available to the Maven-invoked scanner process (not the SonarQube server itself) until you reproduce an OutOfMemoryError during analysis.
  • Identify exactly which JVM process this is (the Maven build's own JVM running the sonar-maven-plugin, distinct from the SonarQube server's JVM), and find the correct mechanism to give it more heap (typically an environment variable or Maven-level JVM argument, not a SonarQube server setting).
  • Confirm increasing memory resolves it.

Scan a real project with both branch analysis and PR analysis (without DevOps platform integration)

Difficulty 5/10Core

Goal: Understand the fundamental difference between branch analysis and PR analysis as mechanisms, on a real (not toy) project.

Where to look, not what to write
  • Using a real, non-trivial project, run a normal branch analysis on its main branch, then run a PR analysis (manually, without any DevOps platform integration configured) representing a feature branch.
  • Compare what each mode actually reports: branch analysis evaluates the full branch state against a New Code period; PR analysis only reports issues introduced by that specific changeset, scoped for merge-gating.

Simulate analyzing a project out of chronological order with sonar.projectDate

Difficulty 10/10Stretch

Goal: Understand the constraint that SonarQube can only "rebuild the past" in chronological order, and what breaks if you violate it.

Where to look, not what to write
  • Run a normal analysis today, then run a SECOND analysis using sonar.projectDate set to a date BEFORE the first one, deliberately going out of order.
  • Observe exactly what happens, does it fail outright, silently produce misleading history, or something else?
  • Note a genuine current limitation while you're at it: there's no built-in API method to simply list every background task's timestamp/history to help spot this kind of ordering problem after the fact, you'd have to reconstruct it from individual api/ce/task?id=... calls.
