1

Find release upgrade notes

Difficulty 1/10Core

Goal: Know how to find release/upgrade notes, why customers often struggle to find them, and how customers are notified of releases and bugfixes.

Model answer

Release/upgrade notes are published alongside each SonarQube release on Sonar's documentation site, but hotfix-specific announcements are less prominently placed and easier to miss than major-version release notes, part of why customers often struggle to find them, discoverability and scattered locations rather than the content being genuinely hidden. Customers are generally notified of releases through documentation/changelog channels they have to actively check (pull), rather than a guaranteed proactive push notification for every fix or dev ticket completion.

Grading notes

Pass: actually located both major release notes and a hotfix announcement, and can articulate the discoverability gap (scattered locations, no guaranteed push notification) rather than just saying "they're on the website."

2

Check the System Info File

Difficulty 1/10Core

Goal: Understand the configuration parameters visible in a System Info File, and how to use it to debug OOMs or performance issues.

Model answer

A System Info File's configuration section exposes JVM/memory-related settings (heap sizes, JVM options per process) alongside general instance configuration; reviewing these against known guidance (heap sized appropriately for instance scale, no obviously undersized settings) is often the first concrete step in triaging an OOM or slow-performance ticket, since it tells you the customer's actual configured state without needing live access to their instance.

Grading notes

Pass: actually downloaded and read a real System Info File and identified specific memory-related settings in it, connecting this to why it's typically the first artifact pulled for a performance ticket.

3

Review and understand logs and different logging levels

Difficulty 1/10Core

Goal: Know how to get INFO, DEBUG, and TRACE level logging, both instance-wide and for individual JVM processes, and how to modify log rolling policy.

Model answer

SonarQube's Elasticsearch indexes live under the data/es8 directory (path may vary by version); the documented fix for corrupted or inconsistent indexes is stopping SonarQube, deleting that directory, and restarting, which triggers a full automatic rebuild. While rebuilding, issue search, the global Issues page, and security reports become unavailable or incomplete (availability is restored progressively, prioritizing recently-analyzed projects); SonarQube also has a built-in resilience mechanism that can self-heal indexes merely behind the database without a full manual delete, worth trying first before the more disruptive manual step.

Grading notes

Pass: correctly identifies the data/es8 directory and the stop-delete-restart mechanism, and knows to try the automatic resilience/self-heal path before resorting to a manual full delete.

4

Review and set the platform prerequisite parameters

Difficulty 1/10Core

Goal: Understand SonarQube's platform-level prerequisites before even attempting an install.

Model answer

A single-project reindex (a targeted POST call under api/issues/) fixes one project showing inconsistent search/issue data, typically after an upgrade or a broader reindex leaves that project's data stale, without touching the rest of the instance. A full instance-wide reindex is heavier and more disruptive (triggered automatically by upgrades/restores, or manually via the data-directory-delete approach), reserved for global corruption rather than a single misbehaving project.

Grading notes

Pass: named the correct single-project API call and can articulate when you'd reach for the narrow fix versus the full, more disruptive reindex.

5

Clear Elasticsearch indexes and observe the impact

Difficulty 2/10Core

Goal: Understand where Elasticsearch indexes live, and why/how they get rebuilt.

Model answer

Each SonarQube process (Web, CE, Search/Elasticsearch) has independent JVM memory settings; Sonar's own guidance recommends keeping -Xms equal to -Xmx per process to avoid runtime heap resizing hurting response times. Rather than memorizing specific numbers (which vary hugely by instance scale), the diagnostic approach is: check whether a process is consistently near its configured heap limit, look for OutOfMemory errors/crashes in sonar.log, and for Compute Engine specifically, watch pending/in-progress/failed task counts and oldest-pending-task wait time, a growing backlog suggests CE needs more heap or workers, not just a temporarily slow queue.

Grading notes

Pass: correctly focuses on diagnostic signals (heap-limit proximity, OOM log entries, CE task backlog trends) rather than inventing specific -Xmx numbers as universally correct, since real-world tuning is workload-dependent.

6

Pause the Compute Engine queue with api/ce/pause and observe the impact

Difficulty 2/10Core

Goal: Understand why pausing CE task processing is a genuinely useful operational tool, not just a curiosity.

Model answer

Log entries across Web, CE, Search, and Access logs for a single request/task share an identifier that lets you trace its full lifecycle end to end, an access log entry, the corresponding web.log detail, and (if it spawned a background task) the ce.log processing record. Raising the log level to DEBUG or TRACE (globally or per-process via sonar.log.level.web/.ce/.es) surfaces more detail including SQL/ES call information; note the exact field name for this correlation ID is worth confirming against a real log sample or the background task's own id field in the API, rather than assuming a fixed universal "UUID" label across all four log types.

Grading notes

Pass: actually cross-referenced the same identifier across at least two of the four log files for a single real request, this is a genuinely useful troubleshooting technique worth having hands-on experience with, even if the exact field naming needs verifying case by case.

7

Tune memory settings for a SonarQube instance

Difficulty 2/10Stretch

Goal: Understand the diagnostic approach for judging whether a customer's JVM memory settings are healthy, without needing to invent specific numbers.

Model answer

A SonarQube service (Windows Service or a Linux systemd unit) gives you auto-start on boot and process supervision/restart, versus a foreground process that dies when the terminal session ends and doesn't restart itself on failure. Running multiple versions/instances as services on the same machine requires distinct service names/configurations (and non-conflicting ports/data directories) for each, rather than a single service definition handling more than one version.

Grading notes

Pass: actually set up a real service on both Windows and Linux, and correctly identifies auto-start/supervision as the core difference from a foreground process, plus a concrete plan for running multiple versions without conflict.

10

Reindex a single project via the Web API

Difficulty 3/10Stretch

Goal: Understand when reindexing one specific project is appropriate versus a full Elasticsearch reindex.

Model answer

Housekeeping (the dbcleaner) matters because without it, a SonarQube database accumulates years of granular historical data (old analysis snapshots, source-level detail from every past analysis) that isn't actually needed for long-term trend visibility, only for the current/recent state; without pruning, this would grow unbounded. It runs automatically as part of routine analysis processing, and can also be influenced/forced via specific settings like sonar.projectDate manipulation or the daysBeforeDeletingInactiveBranchesAndPRs threshold, connecting directly to the equivalent Administration exercise item on this same mechanism.

Grading notes

Pass: explains the unbounded-growth rationale in their own words, and correctly connects this to the same underlying dbcleaner mechanism tested in the Administration exercise, rather than treating it as an unrelated Operations-only concept.

11

Back up and restore a database

Difficulty 3/10Core

Goal: Practice a real database backup and restore cycle for SonarQube's own database.

Model answer

By default, users with Administer Quality Profile permission receive an email whenever a built-in Quality Profile (e.g. "Sonar way") is updated, typically as a side effect of a SonarQube or analyzer version upgrade introducing new or deprecated rules. sonar.builtInQualityProfiles.disableNotificationOnUpdate (default off, meaning notifications are on) lets an admin suppress this; a reasonable admin motivation is notification fatigue, especially at scale managing many instances/upgrades where the notification doesn't drive any actual action since profiles are expected to inherit and auto-update anyway.

14

Set up PostgreSQL as SonarQube's database

Difficulty 4/10Stretch

Goal: Understand how straightforward PostgreSQL setup is compared to other supported databases.

Model answer

Only tasks still in the Pending state can be cancelled (individually or in bulk) via the UI or the api/ce/cancel / cancel_all endpoints; a task already In Progress cannot be cancelled through any documented, supported mechanism, since Compute Engine processes reports serially and is actively writing to the database mid-processing, making a safe mid-flight cancel impossible without risking inconsistent state. If an in-progress task appears stuck, the only supported recourse is checking CE logs for the actual hang, or restarting the CE/server process, there's no force-kill option.

Grading notes

Pass: actually attempted to cancel both a pending and an in-progress task and observed the real difference in what's possible, and correctly states there's no supported force-cancel for an in-progress task.

15

Clone a database to run multiple SonarQube versions against the same data

Difficulty 4/10Core

Goal: Have multiple SonarQube instances running against a copy of the same data, without needing to repopulate it each time.

Model answer

A Portfolio hierarchy has to be a genuine tree; nesting the same Portfolio under two different parents (or under one of its own descendants) creates a structure where recomputation logic breaks, since there's no well-defined "correct" rolled-up value when a node's contribution would need to be counted through more than one path, or the tree becomes circular. In practice this manifests as a recomputation failure, a stuck computation, or visibly incorrect aggregate numbers rather than a clean error explaining the structural problem.

Grading notes

Pass: actually built the duplicated/nested structure and observed a real recomputation failure or misbehavior, and can explain in their own words why a non-tree structure breaks the rollup logic conceptually.

19

Debug a SonarQube server performance problem via logs

Difficulty 5/10Stretch

Goal: Practice going through web, CE, and Elasticsearch logs to diagnose a performance issue the way a real support ticket would require.

Model answer

JMX exposes standard JVM mBeans (ClassLoader, Memory, Threads, OS) plus a few SonarQube-specific ones, all read-only (can't be reset without restarting the process), and each process (Web, CE, Search) needs separate JMX configuration rather than one unified view. A specifically documented limitation: SonarQube's CE task-processing-time metric via JMX is cumulative since the last restart, so it can't show a recent time window in isolation, one of the reasons Sonar's docs now point toward the newer Prometheus-based /api/monitoring/metrics endpoint as the preferred modern alternative.

Grading notes

Pass: actually connected via jconsole (or similar) to a real SonarQube JVM and browsed real mBeans, and correctly names at least one specific documented limitation (read-only, cumulative-since-restart metric, or per-process config) rather than a vague "it's limited."

24

Experiment with Server ID changes

Difficulty 5/10Stretch

Goal: Understand exactly how a Server ID is generated and in which situations it actually changes.

Model answer

DCE's inter-node Elasticsearch encryption has two separate layers: the HTTP layer between app nodes and search nodes (which Sonar's own docs cover, requiring ES auth enabled first, then TLS certs referenced by sonar.cluster.es.http.ssl.keystore), and the ES transport layer between search nodes themselves (port 9300), which is native Elasticsearch mutual-TLS, documented by Elastic rather than Sonar. Enterprises want this because compliance frameworks and strict internal security policy often don't carve out an exception for "internal-only" traffic, an attacker who reaches the internal network segment could otherwise read or manipulate cluster data even though it never crosses a public boundary.

Grading notes

Pass: correctly distinguishes the HTTP layer (Sonar-documented) from the ES transport layer (Elastic-documented, native mutual-TLS) as two separate encryption concerns, and articulates the compliance rationale for encrypting supposedly-internal traffic.

"DCE in a box" runs a full DCE topology (multiple application nodes, shared database, shared Elasticsearch cluster) on a single machine, explicitly for learning/testing purposes, since collapsing everything onto one host defeats DCE's actual HA purpose (a single hardware failure would take down the whole thing).
