What is the SonarQube MCP Server used for, and where does it run?

QuestionCore

Goal: Understand MCP Server architecture and deployment modes.

Where to look, not what to write
  • Start with the overview page: About the MCP Server. What problem is it solving for an AI coding agent that the agent couldn't do on its own?
  • Look at the setup pages for the different hosting shapes: Self-hosted, SonarQube Server-hosted, and SonarQube Cloud-hosted. Note how "runs locally on your machine" differs from "runs as a proxy through your SonarQube instance."
  • Think about who the client is (an IDE, a CLI agent, a chat client) versus who the server is (something that talks to SonarQube on the client's behalf).

What configuration setting should you include if your SonarQube Server has a private certificate (self-signed or internal CA-signed)?

QuestionCore

Goal: Know how to configure private certificates for the MCP server.

Where to look, not what to write
  • Check Environment considerations and the MCP server GitHub repo for how custom certificates are supplied to the container.
  • Think in terms of Docker: what do you mount, and where, so the container's trust store picks up your organization's CA? What certificate formats are accepted?
  • This is the same underlying problem as certificate errors elsewhere in Sonar's stack (compare with the equivalent AI CodeFix question if you've done that exercise) — the fix pattern rhymes.

What configuration setting allows you to run the SonarQube MCP Server with an HTTPS endpoint?

QuestionCore

Goal: Know how to configure HTTPS for the MCP server.

Where to look, not what to write

Can you restrict which MCP tools a user's valid token can reach? How would you monitor MCP server usage, and what makes that hard?

QuestionCore

Goal: Understand security scoping and the practical limits of monitoring MCP server usage.

Where to look, not what to write
  • Look at the SONARQUBE_TOOLSETS and read-only style headers described in the environment variables reference. Can a per-request header expand what a client can reach, or only narrow it?
  • Separately, think about token scope itself: SonarQube token types (user vs. project vs. global) already exist independently of the MCP server. Which type does the MCP server actually require, and what does that imply about the blast radius of a leaked token?
  • For monitoring: what does the MCP server expose today (health/service endpoints, telemetry) versus what a security team would actually want (a full audit trail of which tool a specific user invoked, and on which data)? Where's the gap?

Install the SonarQube MCP Server locally using both the jar and Docker installation methods

TaskCore

Goal: Practice MCP server installation both ways.

Where to look, not what to write
  • Docker path: SonarSource/sonarqube-mcp-server on GitHub has the container image and run command. Jar path: the same repo's releases, or the Build page. The jar requires a specific Java version, note which one.
  • Do both installs against the same SonarQube instance/token so you can compare behavior, not just confirm each one starts.
  • Worth noting for later: the jar path may not be a permanent deployment option. Keep that in mind if you're documenting steps for someone else.

8

Get information about one of your projects from the AI agent via the MCP server, and validate it against the SonarQube UI

TaskCore

Goal: Verify the MCP server actually retrieves correct data, not just that it responds.

Where to look, not what to write
  • Pick a real project you have in SonarQube (Cloud or Server), and ask your agent something concrete: open issue count, quality gate status, a specific rule's findings.
  • Cross-check the agent's answer against the same data in the SonarQube UI. Do the numbers match exactly? If not, is that a caching/timing issue, a scoping issue (wrong branch/project), or something else?
  • This is a good moment to also notice which MCP tool the agent actually called, most agents will show you the tool call, which ties back to the toolset question in task 9.

Test the toolsets-related environment variables and see how the agent's available tools change

TaskStretch

Goal: Deep dive into toolset scoping. Optional, but a good one for understanding least-privilege setups.

Where to look, not what to write
  • Check the toolset-related variable in the environment variables reference and the full toolset list on the Tools reference page.
  • Launch the server with a narrowed toolset list, then ask your agent to do something that would need a tool you excluded. What happens: an error, a silent "can't help with that," or something else?
  • Pay attention to whether specifying a subset replaces the default set entirely, versus just removing what you listed. That distinction matters for anyone locking this down for a team.

Test the SonarQube MCP Server alongside Sonar Vortex agentic analysis and context augmentation

TaskStretch
