What are the use cases for context augmentation and agentic analysis?

QuestionStretch

Goal: Determine realistic use cases for Vortex's two capabilities. Optional, but a good warm-up before the core questions below.

Where to look, not what to write
  • Read the "What Vortex delivers" section on the Vortex onboarding page, and the official Sonar Vortex: context augmentation and Sonar Vortex: agentic analysis pages.
  • Think of a concrete scenario for each: when would a team specifically want an agent to know the repo's architecture and conventions before writing code (context augmentation), versus when would they want fast, in-loop verification after each edit (agentic analysis)?
  • Note that context augmentation and agentic analysis are two separate capabilities under the Vortex name, not one feature, your use cases for each should look different.

Where does context augmentation occur?

QuestionCore

Goal: Understand context augmentation's architecture, specifically where the work actually happens.

Where to look, not what to write
  • This question is explicitly flagged in the source material as needing review, since Sonar Context Augmentation (CAG) and SonarQube Agentic Analysis (AA) were later folded into the unified Sonar Vortex product. If you find older material that still says "CAG," treat it as describing the same underlying mechanism under a different name.
  • Read the setup requirements on Sonar Vortex: context augmentation. Pay close attention to the specific phrase about what kind of MCP server this requires, local versus hosted, and why a hosted MCP server (Cloud-hosted or Server-hosted) is explicitly called out as insufficient.
  • Ask: does the actual context-building/injection work happen on Sonar's servers, or on the machine running the agent? What clue in the setup requirements (filesystem mount, local process) tells you this?

What do you need to enable context augmentation for your project?

QuestionCore

Goal: Know the full prerequisite list for context augmentation, not just the licensing gate.

Where to look, not what to write
  • Start with the "Readiness checklist" on the Vortex onboarding page, then check the prerequisites list on Sonar Vortex: context augmentation for anything more specific.
  • There's more than one layer here: an entitlement/plan gate, an org-level enablement step, a project-level analysis requirement, and something specific about tokens and MCP configuration. Try to identify all four layers rather than stopping at the first one you find.
  • Notice the project-level requirement in particular: what does the project need to have already happened to it before context augmentation is useful, and why would that matter for a brand-new project with no history?

What does context augmentation add to the MCP server?

QuestionCore

Goal: Understand the value and features context augmentation contributes on top of a plain MCP server setup.

Where to look, not what to write
  • If you've done the MCP Server exercise, revisit what the base MCP server gives an agent (data retrieval tools) before answering this one, this question is really asking "what's new beyond that."
  • Read the capability breakdown on Sonar Vortex: context augmentation. There are several distinct categories of capability described, try to name more than one rather than a single generic answer like "more context."
  • Distinguish tools that help the agent understand code it hasn't written yet (navigation, architecture) from tools that shape what it's about to write (guidelines, dependency checks). Which category does each capability fall into?

Use context augmentation with an existing test project

TaskCore

Goal: Get hands-on with context augmentation instead of only reading about it.

Where to look, not what to write
  • Reuse a project you already have analyzed in SonarQube Cloud on a long-lived branch (this is a prerequisite you should have surfaced in question 3).
  • Follow the "Install and run" steps on the Vortex onboarding page, or the walkthrough at Add context to generate better code.
  • Give your agent a real coding task on that project and look for direct evidence it used injected context, cite specific architecture facts, follow a coding convention it couldn't have guessed, or flag a dependency, rather than just producing generic code.
