What are the steps to configure Remediation Agent to operate on a project?

QuestionCore

Goal: Configuration of Remediation Agent.

Model answer
  • Confirm the organization is on SonarQube Cloud Team (annual) or Enterprise, with a Sonar Agent Essentials subscription.
  • Bind the target project to GitHub or Azure DevOps and ensure it has a completed analysis (automatic or CI-based).
  • Add an LLM provider API key (OpenAI or Anthropic) to the organization, since the agent runs on a customer-supplied key, not a Sonar-hosted default.
  • For GitHub: install/connect the SonarQube Agent GitHub App, scoped to read/write on code and pull requests, read-only on issues and metadata.
  • Enable "Pull request fixes" and/or "Backlog fixes" for the target repositories, and, for backlog remediation, an org admin sets a schedule that project admins can override or disable per project.
Grading notes
  • Pass: covers plan/entitlement, DevOps binding, and enabling the specific fix types, in roughly the right order.
  • Watch for staleness: confirm the new joiner mentions the customer-provided LLM key, this is a meaningful detail that may not be reflected in every internal doc yet.

See: Remediation Agent onboarding, Administer Remediation Agent.

What are the different modes of operation for Remediation Agent?

QuestionCore

Goal: Understand operation modes.

Model answer
  • Automated backlog remediation: runs on an org-set schedule, opens PRs for eligible backlog issues grouped by rule key and file type, project admins can override or disable per project. Available on GitHub and Azure DevOps.
  • Manual backlog remediation: a person selects specific issues from the Issues page and clicks "Assign to Agent." Also available on GitHub and Azure DevOps.
  • Pull request remediation: triggered automatically when a PR's quality gate fails due to new issues. GitHub only, not currently available on Azure DevOps.

All three modes share the same underlying verification loop: a candidate fix is generated, applied to a sandbox, re-analyzed, and only posted if it passes. None of the three modes auto-merges, a human always reviews and merges the resulting PR.

Grading notes
  • Pass: names all three modes and correctly identifies that PR remediation is GitHub-only while both backlog modes work on GitHub and Azure DevOps.
  • Common miss: treating "automated" and "manual" backlog remediation as the same thing, they're distinguished by what triggers them (schedule vs. a person's click), not by what they fix.

See: Remediation Agent onboarding, Remediation Agent.

How do you troubleshoot bad results from Remediation Agent?

QuestionCore

Goal: Troubleshooting skills for Remediation Agent.

Model answer
  • Agent never triggers at all: check for an unsupported language (currently C#, Java, JavaScript/TypeScript, Python, plus Secrets fix suggestions and SCA dependency bumps, anything else like C++ won't trigger it even if issues are found); check the PR issue-count cap (PR remediation isn't offered if the PR introduces more than 20 new issues, to avoid comment-history noise); check whether the specific rule is on the excluded "too complex for an LLM" list.
  • Agent triggers but no fix appears: the candidate fix likely failed re-verification, the agent applies the fix to a sandbox and re-runs SonarQube's analysis engine; if that re-analysis still fails, the fix is discarded rather than shown, this is working as intended, not a bug.
  • Configuration/auth issues: missing, invalid, or exhausted LLM provider API key (OpenAI or Anthropic) on the organization; incomplete GitHub App permissions; DevOps platform mismatch (remember PR remediation is GitHub-only).
Grading notes
  • Pass: distinguishes "agent never triggers" (eligibility gate) from "agent triggers but discards its fix" (failed re-verification), these require different troubleshooting paths and a good support answer needs to tell them apart.
  • Strong answer: mentions the 20-issue PR cap specifically, this is a concrete, checkable number that's easy to verify against a real PR.

See: Remediation Agent onboarding, Remediation Agent.

Where is Remediation Agent hosted?

QuestionCore

Goal: Architecture of Remediation Agent.

Model answer

The orchestration and verification logic (reading project context, generating a candidate fix, applying it to a sandbox, re-running SonarQube's analysis engine, posting the verified fix as a PR) runs on Sonar's own remediation service. However, the actual LLM inference call is made under the customer's own provider account: the organization supplies an OpenAI or Anthropic API key, Sonar's service sends the affected code snippet to that provider's model, and usage is billed to the customer's provider account. That means the code sent to the LLM is governed by the customer's own provider usage agreement, not solely Sonar's, since the customer chose and pays for that provider relationship.

Grading notes
  • Pass: separates "where the orchestration/verification runs" (Sonar's service) from "whose account the LLM call is billed to and governed by" (the customer's provider key). This split is the crux of the question.
  • Common miss: saying "it's hosted by Sonar" or "it uses your own LLM" without acknowledging both halves are true simultaneously, for different parts of the pipeline.

See: Remediation Agent onboarding, Remediation Agent.

What's the difference between Remediation Agent and AI CodeFix?

QuestionCore

Goal: Distinguish AI products.

Model answer

AI CodeFix is on-demand and single-issue: a developer clicks "Generate AI Fix" on one specific issue in the Issues page or IDE, and nothing changes until they explicitly Apply. It has no autonomous or scheduled behavior.

Remediation Agent operates at PR and backlog scale, and can run automatically: it monitors PRs for quality gate failures (no click required to trigger detection), and can work through the entire backlog on a schedule an admin sets, without a developer picking each issue one at a time. Every fix is still re-verified before becoming a PR, and a human still merges it, but the triggering is automatic in a way AI CodeFix's is not.

Both are Solve-stage features and both re-scan/preview before anything is applied, the real distinguishing axis is scope (one issue vs. a PR vs. the whole backlog) and trigger (manual click vs. automatic/scheduled).

Grading notes
  • Pass: correctly identifies scope and trigger as the distinguishing axes, not "one uses AI and the other doesn't" (both do) or "one is better than the other" (they're complementary).
  • Bonus: connects this back to AI CodeFix's LLM being Sonar-hosted/chosen (Cloud) or configurable (Server), versus Remediation Agent's customer-supplied provider key, a real architectural difference worth knowing for support.

See: Remediation Agent onboarding, AI CodeFix onboarding.

Review the Hunter Agent onboarding reference page

TaskCore

Goal: Quick, high-level overview of Hunter Agent, a genuinely different product from the rest of this exercise.

Model answer

Hunter Agent is a Verify-stage tool: it hunts for vulnerabilities (broken access control, business-logic flaws, authentication/session issues) that need contextual, human-like judgment rather than pattern matching, and raises them as standard SonarQube issues. It runs entirely on Sonar's own infrastructure and only reads source code, it does not run or attack a live application. Critically, Hunter Agent does not fix what it finds, that's the job of Remediation Agent (or a developer) downstream. The relationship to everything else in this exercise: Hunter Agent is upstream of Remediation Agent in the Verify-then-Solve pipeline, one discovers deep logic-level findings, the other proposes verified fixes for issues (from any source, not just Hunter Agent) already in the backlog or a PR.

Grading notes
  • Pass: correctly states Hunter Agent finds but does not fix issues, and can articulate the Verify-then-Solve relationship to Remediation Agent in one sentence.
