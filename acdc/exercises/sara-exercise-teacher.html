What does SARA actually measure, and what is it explicitly not evaluating?

QuestionCore

Goal: Understand what SARA is a benchmark of.

Model answer

SARA scores "agentic friction," the unwritten knowledge and environmental hurdles that cause AI agents to underperform or act unsafely in a given repository. It benchmarks the repository/environment itself (documentation, workflows, tooling, safety guardrails), not the AI model being used against it. Two teams using the identical AI agent could get very different SARA scores on two different repos, because the thing being scored is how much implicit, undocumented knowledge that repo demands from whoever (human or agent) works in it.

Grading notes
  • Pass: clearly states SARA evaluates the environment/repository, not the model, and can explain why the same agent could score differently on two repos.
  • Common miss: describing SARA as "testing how good the AI is," inverting the actual target of measurement.

See: SARA onboarding.

What are the eight pillars, and how do they map to the three AC/DC stages?

QuestionCore

Goal: Know the pillar model.

Model answer
  • Guide (3 pillars): Documentation and context, Workflow and contribution, Dev environment.
  • Verify (4 pillars): Build system, Testing, Code quality and style, Security.
  • Solve (1 pillar): Observability.

Verify has the most pillars (4), reflecting how much of "agent readiness" comes down to giving an agent fast, reliable, automated feedback on whether its own change worked. Solve has only one (Observability), framed narrowly as "can the agent diagnose failures from structured, machine-readable signals alone," rather than covering fixing/remediation broadly.

Grading notes
  • Pass: names at least 6 of 8 pillars correctly grouped by stage, and notices Verify has the most pillars.
  • Strong answer: restates at least two pillar questions in their own words rather than quoting the page (e.g., "Dev environment" as "can an agent get from a fresh clone to running tests with zero tribal knowledge").

See: SARA onboarding.

What are the five maturity levels, and what's the practical difference between adjacent levels?

QuestionCore

Goal: Be able to explain a level-up in concrete terms.

Model answer
  • L1, Pre-agentic: tooling/guidance exist but lack cohesion (e.g., incomplete README, undocumented setup).
  • L2, Basic: quality gates and docs exist and meet baseline standards, but aren't optimized (e.g., reasonable test coverage, CI checks present).
  • L3, Standardized: an agent-ready baseline, documented conventions, an idempotent build, consistent vocabulary, enough for an agent to work with minimal guidance.
  • L4, Agent optimized: tooling explicitly designed for agent navigation, automated quality gates, comprehensive observability, fast feedback loops.
  • L5, Agent native: fully autonomous workflows, self-describing codebase, machine-readable policies, automatic error recovery.

Example L2→L3 jump: moving from "CI exists and passes" to "conventions are actually documented somewhere an agent could read, and the build is idempotent," the difference between baseline compliance and something an agent can rely on without a human explaining exceptions. And yes: a project's overall level is distinct from any single pillar's level, the runbook explicitly has you open each pillar to see its own breakdown, a project can be strong in some pillars and weak in others while carrying one overall number.

Grading notes
  • Pass: names all five levels roughly in order, and gives one concrete, plausible example of what changes between two adjacent levels.
  • Pass: correctly states overall level and per-pillar level are different numbers.

See: SARA onboarding.

4

What do you need before you can run a SARA assessment?

QuestionCore

Goal: Know the prerequisite gates.

Model answer
  • SonarSource organization only: the alpha-specific gate, SARA is currently scoped to SonarSource-owned organizations, not customers generally. This exists because SARA is alpha and not yet generally available, this will presumably loosen at GA.
  • Feature flag enabled: the org needs agentic readiness assessment turned on to authorize the project page and CLI calls.
  • Project bound and analyzed: the target project must be bound to its repository on SonarQube Cloud, since SARA clones and assesses the default branch directly.
  • SonarQube CLI or MCP access: specifically for agent-triggered runs (as opposed to a person clicking the button in the UI), the agent needs CLI or MCP access to call the assessment API on demand. This is the one prerequisite that's additional for the agent-triggered path, not required for a manual UI-triggered run.
Grading notes
  • Pass: identifies the SonarSource-only scope as alpha-specific, and correctly separates the manual (UI) path's prerequisites from the additional CLI/MCP requirement for agent-triggered runs.

See: SARA onboarding.

What exactly does a SARA assessment evaluate, the working tree or something else?

QuestionCore

Goal: Avoid a common support mistake around local vs. pushed changes.

Model answer

SARA evaluates the project's default branch on SonarQube Cloud, not local uncommitted changes. If a developer makes local fixes and immediately re-runs the assessment without merging or pushing, the report will look unchanged, SARA never saw those changes because it clones and assesses what's on SonarQube Cloud's copy of the default branch. The correct sequence: make the change, merge/push it to the default branch, then re-run the assessment to see the improvement reflected.

Grading notes
  • Pass: correctly states the assessment runs against the default branch on SonarQube Cloud, and can walk through why a naive local-fix-then-rerun wouldn't show improvement.
  • This is a realistic support scenario, if the new joiner can explain it clearly, they're ready to field a similar ticket.

See: SARA onboarding.

What are the three finding categories a SARA report groups results into, and how should they change what you do first?

QuestionCore

Goal: Know how to prioritize a report.

Model answer
  • Blocker: the most severe category, findings that materially prevent or badly hamper agent autonomy, triage these first.
  • Negative: real gaps that hurt readiness but don't block outright, work through these after Blockers.
  • Positive: things already working well, useful context but not action items.

Blockers should be triaged first, per the onboarding page's own "Definition of a successful onboarding" (an "Actioned" project triages Blocker findings first), because they represent the findings most likely to actively prevent an agent from working safely or effectively, fixing lower-severity Negatives first while a Blocker sits unresolved wastes effort on marginal gains.

Grading notes
  • Pass: names all three categories and correctly states Blocker findings should be triaged first.

See: SARA onboarding.

7

Run a SARA assessment on a project you have access to

TaskCore

Goal: Hands-on experience with an actual run.

What to check

Given SARA's alpha, SonarSource-only scope, it's entirely plausible some new joiners won't have qualifying access yet. Accept "I don't have access, here's who I asked" as a complete, passing answer to this task, don't require a completed run if access genuinely isn't available. If they did run it, confirm they can state the actual overall level and at least one pillar score they got back.

Grading notes
  • Pass (with access): names the project, overall level, and at least one pillar score.
  • Pass (without access): clearly documents the access blocker and who they asked to resolve it, don't penalize for an infrastructure gap outside their control.
8

Pick one Blocker or Negative finding from your report and work through the recommended action

TaskCore

Goal: Practice the close-the-gap loop.

What to check

Look for an actual attempted fix, not just a restated recommendation. If they could re-run and confirm the finding cleared, that's the strongest evidence of understanding the full loop (find → fix → merge → re-run → confirm). If they couldn't complete the loop within the exercise, a clear description of what they did and what they'd expect to happen is an acceptable partial.

Grading notes
  • Pass: names the specific finding, describes the concrete change attempted, and reports the outcome (cleared, partially addressed, or not yet re-run with a clear reason why).
