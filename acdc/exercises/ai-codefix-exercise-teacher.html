What's the difference between AI CodeFix, Sonar Vortex agentic analysis, the Remediation Agent, and Vortex context augmentation?

QuestionCore

Goal: Understand differences between Sonar AI features.

Model answer
  • AI CodeFix (Solve): on-demand, single-issue fix suggestion. A developer clicks "Generate AI Fix" on one issue; nothing changes until they Apply.
  • Vortex context augmentation (Guide): injects repo maps, architecture rules, and conventions into a coding agent's prompt before it writes code. Not a fix generator, it's pre-writing context.
  • Vortex agentic analysis (Verify): reuses CI analysis context to run SonarQube's deterministic checks on edited files in seconds, inside the agent's own loop, so the agent can self-correct before a PR.
  • Remediation Agent (Solve): operates at PR and backlog scale, not single-issue. It fixes PR quality-gate failures and works through backlog issues, always re-scanning a candidate fix before opening it as a PR.

Key distinguishing axis: trigger (on-demand click vs. automatic/scheduled) and scope (one issue vs. a PR vs. the whole backlog vs. pre-write context).

Grading notes
  • Pass: correctly separates AI CodeFix (single issue, on-demand) from Remediation Agent (PR/backlog scale), and can explain Vortex as two separate capabilities (Guide vs. Verify), not one thing.
  • Common miss: conflating AI CodeFix and Remediation Agent because both "use AI to fix code." Probe on trigger and scope if the answer is vague here.
  • Common miss: describing Vortex as a single feature. Context augmentation and agentic analysis are separately enabled and serve different stages.

See: AI CodeFix onboarding, Vortex onboarding, Remediation Agent onboarding.

What does each of these products/features do, and where does each one operate?

QuestionCore

Goal: Understand AI product functionality and location in the stack.

Model answer
  • AI CodeFix operates in the Issues page UI and in SonarQube for VS Code/IntelliJ (connected mode). On GitHub/Azure DevOps-bound Cloud projects, a fix can also open directly as a PR.
  • Vortex context augmentation operates inside a supported coding agent (Claude Code, Codex, Cursor, GitHub Copilot CLI, Antigravity, Kiro) or via the SonarQube MCP server, injecting context into the agent's prompt.
  • Vortex agentic analysis also runs inside the agent's loop, verifying edited files against SonarQube's rule engine as the agent works, reusing a prior CI analysis.
  • Remediation Agent operates against GitHub (PR fixes and backlog) and Azure DevOps (backlog only), triggered from a PR bot comment or the Issues page "Assign to Agent" action.
Grading notes
  • Pass: correctly places at least 3 of the 4 features in the right surface (UI page, IDE, agent loop, PR/backlog).
  • Look for the new joiner distinguishing "runs where the developer already is" (IDE, Issues page) from "runs inside the agent's own reasoning" (Vortex) from "runs against source control automatically" (Remediation Agent).

What are common issues setting up AI CodeFix?

QuestionCore

Goal: Troubleshoot AI CodeFix setup.

Model answer
  • Plan/edition gate: Cloud needs Team (annual) or Enterprise; Server needs Enterprise or Data Center, not Community or Developer. A customer on the wrong plan/edition won't see the setting at all.
  • Wrong admin role: Cloud requires an Organization Admin; Server requires an Instance Admin. A project-level admin can't enable it.
  • No LLM decision made / default not chosen deliberately: especially on Server, where there's a real choice between Sonar-hosted OpenAI and BYO (Azure OpenAI, Bedrock, self-hosted gateway).
  • Network path blocked: outbound HTTPS to the Sonar-hosted endpoint (api.sonarqube.io) is blocked by firewall/proxy, especially in locked-down enterprise networks.
  • Language/rule not eligible: the issue's language or specific rule isn't on the AI CodeFix-eligible list, so "Generate AI Fix" simply doesn't appear, easily mistaken for a bug.
  • Scoped to selected projects, new project not added: if scope is "Only selected projects," new projects aren't auto-included.
Grading notes
  • Pass: at least 3 distinct causes, ideally spanning entitlement, network, and eligibility (not three variations of the same root cause).
  • Strong answer: explicitly separates Cloud-specific causes (plan) from Server-specific ones (edition, BYO-LLM config, air-gapped network).

Why do you need to allow communication to the AI CodeFix service if you have a locally hosted LLM?

QuestionCore

Goal: Understand architectural requirements for local LLMs.

Flagged in source catalog: "Review this further"Treat this as an open question, not a settled one. Grade generously on reasoning; don't expect a crisp final answer.
Best current understanding

Even with a self-hosted or BYO-LLM configured for the actual fix-generation call, the instance still needs outbound reachability to whichever LLM endpoint is configured, that's the model-serving path itself, not a Sonar-hosted dependency. Separately, AI CodeFix as a licensed feature may still involve calls back to Sonar-operated infrastructure for entitlement/licensing checks, rule metadata, or telemetry, independent of where the LLM inference happens. The documented "air-gapped" claim on Server is that prompts and rule metadata ship with the product, so a fully self-hosted LLM setup does not need internet access for the prompt content itself, but confirm this against current Server docs before stating it as settled fact to a customer.

Grading notes
  • Pass: the new joiner distinguishes "reaching the LLM endpoint itself" from "reaching Sonar's own service for licensing/metadata," and correctly flags this as an area with some ambiguity rather than stating a confident wrong answer.
  • This is a good item to discuss live rather than grade purely from the written answer, since the source material itself is marked for review. If the new joiner surfaces the same ambiguity you see here, that's a strong signal, not a gap.
  • Follow up: has Server documentation been updated since this exercise was written? If so, update this teacher key and the flag in the student page.

What causes a certificate error when connecting to the AI CodeFix service?

QuestionCore

Goal: Troubleshoot certificate errors.

Model answer
  • A TLS-intercepting proxy or firewall in the customer's network path presents its own certificate (often self-signed or signed by an internal/private CA) instead of letting the connection to the Sonar/LLM endpoint pass through untouched.
  • The SonarQube instance's Java trust store doesn't include that internal CA's root certificate, so the TLS handshake fails validation.
  • Less commonly: an expired certificate somewhere in the chain, a hostname mismatch (e.g., a proxy rewriting the endpoint), or outdated CA bundles on an older instance.
  • Fix pattern: import the internal/private CA certificate into the instance's trust store (this is the same fix pattern used for the SonarQube MCP server's private-certificate configuration).
Grading notes
  • Pass: identifies a proxy/internal CA as the likely cause and trust store import as the fix, even in general terms.
  • Bonus: connects this to the same class of problem in the MCP Server section of the full catalog, showing they're building a general mental model rather than memorizing per-feature facts.
