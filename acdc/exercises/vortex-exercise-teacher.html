What are the use cases for context augmentation and agentic analysis?

QuestionStretch, optional

Goal: Determine use cases. Marked "not highly suggested" in the source catalog, treat as a stretch/warm-up question.

Model answer
  • Context augmentation: a team with strong internal architecture rules, security policies, or coding conventions that a generic agent wouldn't know, onboarding an agent to a large legacy codebase where blind file exploration wastes tokens, or a team that wants agent-generated code to actually match house style on the first pass instead of needing heavy review rework.
  • Agentic analysis: a team that wants an agent to catch its own bugs before opening a PR, reducing CI round-trips and reviewer burden, especially useful for junior-to-mid agents that would otherwise need a human to catch deterministic issues (null derefs, security hotspots) that SonarQube already knows how to find.
Grading notes
  • This is optional, don't block onboarding completion on it.
  • Pass (if attempted): gives a genuinely distinct use case for each capability rather than one generic "helps the AI write better code" answer that could apply to either.

See: Vortex onboarding, Sonar Vortex: context augmentation, Sonar Vortex: agentic analysis.

Where does context augmentation occur?

QuestionCore

Goal: Understand context augmentation architecture.

Flagged in source catalog: "These need review as this was changed from CAG to Vortex"The underlying mechanism hasn't changed, only the branding: Sonar Context Augmentation (CAG) and SonarQube Agentic Analysis (AA) were unified into the single Sonar Vortex product. Grade on the mechanism, not on whether they use the old or new name.
Model answer

Context augmentation runs locally, on the machine running the coding agent, not on Sonar's servers. It's delivered either through the SonarQube CLI-installed skill or through a locally running SonarQube MCP Server with a local filesystem mount. This is explicitly required: a SonarQube-hosted MCP server, whether SonarQube Cloud-hosted or SonarQube Server-hosted, cannot serve context augmentation tools. The context-building work (reading the repo, assembling architecture/guideline data, injecting it into the agent's prompt) happens client-side; SonarQube Cloud is the source of the underlying issue history and architecture data that gets pulled down and injected, not the place doing the injecting.

Grading notes
  • Pass: identifies that this runs locally/client-side, tied to a local MCP server or CLI skill, and explicitly cannot come from a hosted MCP server.
  • Common miss: answering "in SonarQube Cloud," conflating where the underlying data comes from with where the augmentation work actually happens.

See: Sonar Vortex: context augmentation.

What do you need to enable context augmentation for your project?

QuestionCore

Goal: Prerequisites for context augmentation.

Model answer
  • Plan/entitlement: SonarQube Cloud Team (annual) or Enterprise plan, plus a separate Sonar Agent Essentials subscription.
  • Org-level enablement: an Organization Admin must enable it under SonarQube Cloud's agent-centric development settings; without this, no context augmentation tools appear in the MCP connection at all.
  • Project-level analysis: the project needs to already be analyzed on a long-lived branch (e.g., main). Without a prior analysis, there's no issue history to generate guidelines from and no architecture data to expose, a brand-new, never-scanned project has nothing for context augmentation to draw on. Note: Automatic Analysis is not sufficient for Java projects, CI-based analysis is recommended there.
  • Local MCP/token setup: a locally running SonarQube MCP Server (not hosted), a valid personal access token exported as SONARQUBE_TOKEN, a project-specific MCP configuration (not the global one), and the toolset configuration enabling the relevant toolset (historically cag, now unified under vortex).
Grading notes
  • Pass: names at least 3 of the 4 layers (plan/entitlement, org enablement, project analysis history, local MCP/token config).
  • Strong answer: explicitly explains why a never-analyzed project can't benefit yet, that's the layer most likely to get skipped in a quick answer.

See: Vortex onboarding, Sonar Vortex: context augmentation.

What does context augmentation add to the MCP server?

QuestionCore

Goal: Value and features of context augmentation.

Model answer
  • Architectural awareness: lets the agent navigate class hierarchies, trace call flows, and understand execution paths, using semantic data from SonarQube Cloud's Architecture feature, including user-defined intended-architecture constraints.
  • Intelligent guidelines: automatically injects relevant Sonar rules and quality/security requirements, selected based on the project's historical issues and what the agent's current prompt is actually about to do.
  • Semantic navigation: finds code by meaning (symbols, references, types, call flows) instead of text search, cutting token usage from blind file reads and reducing missed related locations.
  • Dependency health checks: assesses whether a third-party dependency is safe to introduce or update, covering known vulnerabilities, supply-chain malware, and license compliance.

In short: it doesn't add new data-retrieval tools so much as it adds proactive, pre-write intelligence on top of the MCP server's existing surface.

Grading notes
  • Pass: names at least 2 of the 4 capability categories with a correct one-line description of each, not just a list of buzzwords.
  • Strong answer: connects this back to question 2 by noting these capabilities only work with a local MCP server, since they're delivered client-side.

See: Sonar Vortex: context augmentation, MCP Server tools reference.

Use context augmentation with an existing test project

TaskCore

Goal: Hands-on context augmentation usage.

What to check

Look for concrete evidence, not just "I set it up." Did the agent visibly cite an architecture fact, follow a specific project convention, or flag a dependency risk that it couldn't have known without the injected context? A generic "the AI wrote code" report doesn't demonstrate the feature actually fired.

Grading notes
  • Pass: names the project used (should already have CI analysis history per question 3) and describes at least one specific, attributable instance of injected context changing the agent's behavior.
  • If they hit a setup snag (e.g., used a hosted MCP server by mistake, or a project with no analysis history), that's a good diagnostic, ask them to connect it back to question 2 or 3.

See: Add context to generate better code.
