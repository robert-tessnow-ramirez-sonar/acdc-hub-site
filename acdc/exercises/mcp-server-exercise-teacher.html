What is the SonarQube MCP Server used for, and where does it run?

QuestionCore

Goal: Understand MCP Server architecture and deployment modes.

Model answer

The SonarQube MCP Server exposes SonarQube's code quality and security data and analysis capabilities as tools an AI agent can call directly, via the Model Context Protocol, instead of the agent guessing or text-searching. It typically runs locally alongside the developer's agent (as a Docker container or standalone jar), but it can also be hosted differently depending on the setup: self-hosted (you run it yourself), SonarQube Server-hosted (SonarQube Server itself proxies it at <YourSonarQubeURL>/mcp), or SonarQube Cloud-hosted.

Grading notes
  • Pass: correctly identifies it as a bridge/tool layer between an AI agent and SonarQube, and names at least two of the three hosting shapes (self-hosted, Server-hosted, Cloud-hosted).
  • Common miss: describing it only as "a Docker container," missing that it can also run as a jar or be proxied through SonarQube Server itself.

See: About the MCP Server, Self-hosted, Server-hosted.

What does it mean to integrate the SonarQube MCP Server with SonarQube for IDE?

QuestionCore

Goal: Understand the IDE integration.

Model answer

When SonarQube for IDE is running in connected mode and wired up to the MCP server, the MCP server can trigger a real on-the-fly analysis directly in the editor, the same analysis SonarQube for IDE would normally run itself, instead of only returning previously-known data. Most IDEs with an agent-enabled setup (VS Code, Cursor, etc.) surface a one-click "Configure MCP Server" action from the Connected Mode view once connected mode is already set up, which reuses the connected mode credentials. Setup requires a SonarQube user token specifically; project tokens, global tokens, and scoped organization tokens are explicitly not supported for this binding.

Grading notes
  • Pass: identifies that the integration lets the MCP server trigger live analysis in the editor (not just fetch static data), and correctly names user token as the required token type.
  • Bonus: mentions the Linux Docker networking caveat (container can't reach the IDE's embedded server on localhost without --network=host), a real-world gotcha worth knowing for support.

See: Integrate with SonarQube for IDE.

What configuration setting should you include if your SonarQube Server has a private certificate (self-signed or internal CA-signed)?

QuestionCore

Goal: Configuration of private certificates.

Model answer

Mount a directory containing your certificate(s) into the MCP server's Docker container at /usr/local/share/ca-certificates/, for example: -v /path/to/your/certificates/:/usr/local/share/ca-certificates/:ro. Certificates placed there are automatically installed into the container's trust store on startup. Several formats are supported; PEM files split into separate .crt/.key pairs need to be converted to PKCS12 first (openssl pkcs12 -export -in client.crt -inkey client.key -out client.p12) before they'll work. If you're using SonarQube Server's own MCP proxy instead of a standalone MCP server, the equivalent fix is importing the CA certificate into SonarQube's JVM truststore via the caCerts feature.

Grading notes
  • Pass: names the certificate mount path/mechanism for Docker, even without exact syntax memorized.
  • Strong answer: also mentions the PEM-to-PKCS12 conversion requirement, or the separate JVM truststore path for the Server-hosted proxy mode.

See: Environment considerations, GitHub repo.

What configuration setting allows you to run the SonarQube MCP Server with an HTTPS endpoint?

QuestionCore

Goal: Configuration of HTTPS for MCP.

Model answer

The server supports three transport modes: Stdio (the default, recommended for local single-user development), Streamable HTTP over plain HTTP, and Streamable HTTP over TLS (HTTPS). Switching to HTTPS uses the same environment variables as the HTTP transport mode, but also requires configuring a TLS certificate/keystore for the server. HTTPS is the recommended choice for any multi-user or production deployment; HTTP should be limited to trusted internal networks or local testing.

Grading notes
  • Pass: names Streamable HTTP with TLS as the mechanism, and explains why it's preferred over plain HTTP for anything beyond local testing.
  • Watch for: confusing this with the older SSE-only HTTP transport from earlier MCP protocol versions, that's deprecated and not what current SonarQube MCP Server documentation describes.

See: Environment considerations, Environment variables reference.

Can you restrict which MCP tools a user's valid token can reach? How would you monitor MCP server usage, and what makes that hard?

QuestionCore

Goal: Security and monitoring of MCP servers.

Model answer
  • Restriction: In Streamable HTTP mode, a client can send a SONARQUBE_TOOLSETS (and a read-only equivalent) header per request to narrow the tool set for that request. Critically, these headers can only reduce scope below what the server was launched with, they can never expand it or grant a tool the server-level config excluded. A leaked or overly-broad user token is still bounded by whatever toolset the server itself was started with.
  • Token scope itself: the MCP server requires a SonarQube user token, which carries all the permissions of the user who issued it, not a narrowly-scoped project token. That means the practical security boundary is largely "which user issued this token," not anything MCP-specific.
  • Monitoring: the server exposes some unauthenticated service endpoints in HTTP/HTTPS mode intended for health/orchestration checks, and it emits anonymous, non-sensitive usage telemetry to Sonar (disableable via TELEMETRY_DISABLED). What's genuinely hard: there isn't a built-in, per-user audit trail of "which tool did this specific person invoke, against what data." Any real audit trail today has to be reconstructed from SonarQube's own request logs and token metadata, not from anything the MCP server itself logs.
Grading notes
  • Pass: correctly states that toolset headers can narrow but not expand scope, and identifies the lack of a built-in per-user audit trail as the core monitoring gap.
  • Strong answer: connects token scoping back to standard SonarQube token types rather than treating it as an MCP-specific mechanism, since the MCP server inherits whatever the underlying user token can already do.
  • This is a good one to discuss live: docs move fast here, confirm the new joiner checked current documentation rather than relying purely on general MCP security intuition.

See: Environment variables reference, Managing your tokens.

Install the SonarQube MCP Server locally using both the jar and Docker installation methods

TaskCore

Goal: Practice MCP server installation.

What to check

Confirm both installs actually connected to a real SonarQube instance and exposed tools to an agent, not just that a process started. For the Docker path, the recommended image is sonarsource/sonarqube-mcp; note whether they used --pull=always and understand why (Docker caches images locally, so it won't auto-update). For the jar path, confirm they used a compatible Java version and can name it.

Grading notes
  • Pass: both installs demonstrated working against the same instance, and they can articulate at least one practical tradeoff between the two (e.g., Docker handles dependencies/updates more cleanly; jar has no container runtime dependency).
  • Flag for future updates: the jar install path is called out in the source catalog as possibly not a permanent deployment option, revisit this task if that changes.

9

Test the toolsets-related environment variables and see how the agent's available tools change

TaskStretch, optional

Goal: Deep dive into toolsets env variables. Marked "not highly suggested" in the source catalog, treat as a stretch goal.

Model answer / what to check

The relevant variable is SONARQUBE_TOOLSETS, a comma-separated list from: analysis, coverage, dependency-risks, duplications, quality-gates, issues, measures, projects, rules, security-hotspots (the projects toolset is always on and doesn't need to be listed). The important behavior to verify hands-on: specifying a subset replaces the default configuration rather than removing individual items from it, so listing only issues,projects means quality-gates and security-hotspots tools disappear too, even though they weren't the target.

Grading notes
  • This is optional, don't block onboarding completion on it. Use as a signal of initiative if attempted.
  • Pass (if attempted): correctly demonstrates or describes the "replace, not subtract" behavior, that's the non-obvious part worth testing hands-on rather than just reading about.

See: Environment variables reference, Tools reference.
