1

Create a PR on one of the DevOps platforms

Difficulty 1/10Core

Goal: Know the Git basics (clone/pull/push/commit) and how repos/branches work, before layering any SonarQube integration on top.

Model answer

The core Git flow is clone (get a local copy), create a branch, commit changes, push the branch, then open a pull request against the target branch on whichever platform (GitHub, GitLab, Bitbucket, or Azure DevOps) hosts the repo. Every later exercise in this catalog assumes this flow is already comfortable, since PR decoration, pipelines, and branch policies all operate on top of a real pull request.

Grading notes

Pass: actually created a real PR (not just described the steps) and can name the platform and repo used. This is a gating prerequisite, not a deep exercise, don't over-scrutinize it.

2

Set up a webhook (global or project level)

Difficulty 2/10Core

Goal: Understand how a SonarQube webhook is triggered and what information it can carry.

Model answer

A webhook is configured with a target URL (globally under Administration, or per-project) and fires an HTTP POST after an analysis completes, carrying the analysis/Quality Gate result as a JSON payload. Optional configuration includes a secret used to sign the payload (so the receiver can verify it really came from SonarQube) and, on some versions, additional custom properties. A receiving system typically uses this to trigger a downstream action, deploy, chat notification, or a custom dashboard update, based on the Quality Gate outcome without polling the API.

Grading notes

Pass: actually triggered a webhook and inspected a real payload (not just read documentation about the shape), and can name at least one realistic downstream use case for the payload.

3

Set up a Quality Gate wait step on top of your pipeline

Difficulty 3/10Core

Goal: Understand how a pipeline waits for the Quality Gate result, and how to troubleshoot the most common failure mode: timeouts.

Model answer

A "wait for Quality Gate" step blocks the pipeline until SonarQube's background analysis task finishes and reports Pass/Fail, then the pipeline reflects that result. The most common cause of this step timing out is the background task taking longer than the step's configured wait window, often due to a busy Compute Engine queue, a large project taking longer to process, or a network path between the CI runner and SonarQube being slow or blocked. First things to check: the actual background task status/duration in SonarQube's own Background Tasks admin page, and whether the CI runner can reach SonarQube at all during that window.

Grading notes

Pass: correctly identifies that the wait step polls for the background task's completion (not the scan submission itself), and names background task processing time or network reachability as the two most likely timeout causes.

4

PR analysis without a DevOps platform integration

Difficulty 3/10CorePick one

Goal: Understand how PR analysis behaves differently when there's no DevOps platform integration configured, and see how that affects the resulting PR decoration.

Model answer

Without a DevOps platform integration, PR analysis still runs and produces results visible in SonarQube's own UI (issues, Quality Gate status against the PR's code), but the PR decoration feature itself (inline annotations, a status check/comment on the PR in the DevOps platform's own interface) does not appear, since that's exactly what the platform integration exists to deliver. In other words, the analysis still happens; only the automatic surfacing of results back into the DevOps platform's own PR view is missing.

Grading notes

Pass: correctly separates "analysis still runs and is visible in SonarQube" from "decoration on the PR itself is what's missing," rather than assuming PR analysis entirely fails without an integration.

5

Set up pipelines on GitHub, GitLab, Azure DevOps, and Bitbucket

Difficulty 4/10Core

Goal: Understand how to set up a working CI pipeline across multiple different CI platforms.

Model answer

Each CI platform's pipeline definition differs mainly in YAML structure and how it references SonarQube: Azure DevOps pipelines reference a Service Connection and a dedicated SonarQube extension/task; GitHub Actions uses a marketplace Action (or the SonarScanner CLI directly) with secrets stored in repo/org settings; GitLab CI defines stages/jobs directly in .gitlab-ci.yml, often invoking the scanner as a script step; Bitbucket Pipelines uses bitbucket-pipelines.yml with a similar script-step pattern. The concept (checkout, build, scan) is the same everywhere; the syntax and credential-wiring mechanism is what genuinely differs.

Grading notes

Pass: got a successful analysis from at least 2-3 platforms (doesn't need to be all four) and can articulate a specific syntax/mechanism difference rather than a vague "they're all a bit different."

6

PR decoration for Azure DevOps

Difficulty 5/10CorePick one

Goal: Observe PR decoration working end to end on Azure DevOps, and know how to troubleshoot it via Compute Engine logs.

Model answer

With Compute Engine (CE) logs at INFO/DEBUG level, you can watch SonarQube retrieve the PR's metadata from Azure DevOps and post the decoration back, useful for pinpointing exactly where a failure occurs (auth, API call, payload). Azure DevOps pipelines come in two flavors: "classic" (built via the visual designer, stored as JSON internally) and YAML/Infrastructure-as-Code pipelines (defined directly in a checked-in .yml file); a classic pipeline's YAML-equivalent view can usually be exported/viewed from its own UI, useful when a customer only has a classic pipeline to share for troubleshooting.

Grading notes

Pass: actually watched CE logs during a real PR decoration run on ADO, and correctly distinguishes classic (UI-designed, JSON-backed) from YAML/IaC pipelines, including how to get a YAML view of a classic one.

7

PR decoration for Bitbucket Cloud

Difficulty 5/10CorePick one

Goal: Observe PR decoration working end to end on Bitbucket Cloud, including plan-tier limitations.

Model answer

With CE logs at INFO/DEBUG level during a Bitbucket Cloud PR analysis, you can trace the decoration request being posted. The Quality Gate/analysis result appears directly in the Bitbucket Cloud PR view as a build/check status. Bitbucket Cloud's free tier has a limited number of build minutes per month; a customer running frequent PR analyses on a free or lower-tier plan can exhaust this allotment, which would show up as pipeline runs failing to start or being throttled, not a SonarQube-side problem at all.

Grading notes

Pass: confirms where the result surfaces in Bitbucket Cloud's own UI, and correctly frames the build-minute limitation as a Bitbucket plan constraint, not a SonarQube integration bug, an important distinction for triaging a real ticket.

PR decoration for GitLab

Goal: Observe PR (merge request) decoration working end to end on GitLab.

Model answer

With CE logs at INFO/DEBUG during a GitLab merge request analysis, you can trace the decoration call to GitLab's API. Build/job logs are downloadable directly from a pipeline's job view in GitLab's own UI, useful to cross-reference against SonarQube's CE logs for the same run when troubleshooting a discrepancy.

Grading notes

10

Set up SSO header authentication

Difficulty 5/10Stretch

Goal: Understand HTTP header-based SSO, where SonarQube trusts headers set by an upstream proxy instead of handling login itself.

Model answer

SSO header authentication has SonarQube trust specific HTTP headers (a login header, and optionally name/email headers) as proof of identity, assuming an upstream reverse proxy already authenticated the user and set those headers before the request reaches SonarQube. Since standing up a real proxy just for testing is overkill, a browser extension that injects custom request headers can simulate this: setting the configured login header (and name/email headers) causes SonarQube to treat the request as an authenticated session for that user. Without the headers present, the request falls back to SonarQube's normal login page/flow rather than being silently rejected.

Grading notes

Pass: actually used a header-injecting extension to authenticate, and confirms the fallback behavior (normal login) when headers are absent, rather than assuming an error state. Bonus: notes the exact property names used, since these can shift slightly across versions.

11

Set LDAP authentication

Difficulty 5/10Stretch

Goal: Understand the LDAP authentication model and how SonarQube talks to an LDAP directory.

Model answer

LDAP authentication has SonarQube bind to an LDAP directory using configured server URL, bind credentials, and user/group search base settings, then validate a login attempt against that directory rather than SonarQube's own local user store. Group mapping (an LDAP group translating into a SonarQube group) generally requires additional group-mapping configuration beyond just the basic authentication settings, it isn't automatic just because authentication succeeds.

Grading notes

Pass: actually connected to a real (even if disposable/test) LDAP server and successfully authenticated, and investigated group mapping as a separate configuration concern from basic auth rather than assuming it's automatic.

12

Set GitHub authentication

Difficulty 5/10Stretch

Goal: Understand how GitHub-based authentication works, including how GitHub teams/organizations map into SonarQube groups.

Model answer

GitHub authentication is configured via a registered GitHub OAuth App or GitHub App, with SonarQube's settings pointing at its client ID/secret; logging in via "Log in with GitHub" redirects through GitHub's OAuth flow and back into SonarQube as an authenticated user. GitHub org/team membership does not automatically sync into SonarQube group membership just from authentication alone, that requires the separate GitHub provisioning feature (see the provisioning item later in this exercise) to be explicitly enabled; authentication alone only proves identity.

Grading notes

Pass: correctly separates authentication (proving who you are) from provisioning/group-sync (a separate, additional feature), rather than assuming GitHub team membership flows into SonarQube automatically once login works.

13

Set up SAML authentication using OKTA

Difficulty 5/10CorePick one

Goal: Understand the SAML protocol well enough to wire up a real identity provider, using OKTA as a free, accessible option.

Model answer

SAML authentication involves configuring SonarQube as a Service Provider (SP) pointed at an Identity Provider's (IdP) metadata: entity ID, SSO URL, and signing certificate, plus attribute mappings so SonarQube knows which SAML assertion attributes map to username/email/groups. OKTA's free developer/Integrator plan is an easy, real IdP to test against: create a SAML app in OKTA, configure matching settings on the SonarQube side, and testing the full login redirect (SonarQube -> OKTA -> back to SonarQube authenticated) confirms the trust relationship is correctly established. A mismatched entity ID or wrong attribute name typically surfaces as a SAML validation error either on the IdP's side before redirect, or as a failed/incomplete login back on SonarQube.

Grading notes

Pass: actually completed a full SAML login round-trip against a real OKTA instance, and can name at least the core fields involved (entity ID, SSO URL, certificate, attribute mapping).

14

Set up SAML authentication using Azure AD (Entra ID)

Difficulty 5/10StretchPick one

Goal: Understand the SAML protocol using a second real-world identity provider, Azure AD/Entra ID, and compare the experience to OKTA.

Model answer

The SAML concepts are identical to OKTA (entity ID, SSO URL, certificate, attribute mapping), but Azure AD/Entra ID's admin UI and terminology differ: it's registered as an "Enterprise application" with SAML SSO configured under that app's own SAML settings blade, and attribute/claim mapping uses Azure's claims configuration UI rather than OKTA's attribute statements screen. A free-tier personal Azure AD tenant is sufficient for this test, no paid subscription required.

Grading notes

Pass: actually completed a SAML login against a real Azure AD tenant, and can articulate at least one concrete difference in setup experience from OKTA (terminology, UI location, or claims mapping) rather than saying "it's basically the same."

15

Set up Jenkins and scan a project with it

Difficulty 7/10Stretch

Goal: Understand Jenkins well enough to connect it to a DevOps platform and run a real scan, including Jenkins' own architecture.

Model answer

Jenkins connects to a DevOps platform by configuring source control credentials (SSH key or token) and, for PR-triggered builds, a plugin (GitHub/Bitbucket) that lets a job watch for and check out a specific PR/branch. A SonarQube scanner step is then added to that job (either the SonarScanner plugin's build step, or a CLI invocation), and a successful build reports analysis results back to SonarQube. On Windows specifically, scanning a C/C++ project introduces its own build-toolchain considerations (compiler availability, build-wrapper usage) distinct from a typical Linux/Java job. Jenkins pipeline jobs are defined as code (Jenkinsfile); freestyle jobs are configured via the UI form-by-form. Configuration (Java version, secrets/credentials store, executable paths, logs) lives in Jenkins' own system configuration and credentials store, separate from anything SonarQube-side. Jenkins' architecture separates a controller (formerly "master") that schedules and coordinates work from one or more agents that actually execute build steps, which matters for troubleshooting where a given job's environment/tools actually live.

Grading notes

Pass: actually connected a real repo to Jenkins and got a successful scan, and can correctly distinguish pipeline vs. freestyle jobs and controller/agent (master/agent) architecture, these are foundational Jenkins concepts that come up constantly in support tickets regardless of the specific issue.

16

Set up GitHub user/group provisioning

Difficulty 9/10Stretch

Goal: Understand automatic user and group provisioning from GitHub, including exactly when sync happens.

Model answer

GitHub provisioning builds on top of GitHub authentication (must be configured first) and, once enabled, calls GitHub's organization/team membership APIs to keep SonarQube users and groups in sync automatically going forward. A user who already existed in SonarQube before provisioning was enabled is not automatically reconciled, they may need to be manually re-provisioned or will sync on their next relevant event, and removing a user/team on GitHub's side is reflected in SonarQube accordingly (though the exact trigger, real-time vs. next-login vs. scheduled, is version-dependent and worth confirming against current docs rather than assuming one behavior).

Grading notes

Pass: correctly identifies GitHub authentication as a hard prerequisite, and investigated (rather than assumed) what happens to pre-existing users and the actual sync timing, since this is exactly the kind of detail that's easy to get wrong without testing.

Set up GitLab user/group provisioning

Difficulty 9/10Stretch

Model answer

GitLab provisioning similarly builds on top of GitLab authentication and calls GitLab's group/membership APIs to sync users and groups going forward. Grading notes

18

Set up SCIM provisioning on OKTA

Difficulty 9/10Stretch

Goal: Understand SCIM as a provisioning protocol, distinct from SAML authentication, including its stricter network requirements.

Model answer

SCIM is a provisioning protocol distinct from SAML authentication, once enabled, OKTA pushes user/group changes to SonarQube via SCIM API calls rather than SonarQube pulling on login. Users/groups assigned in OKTA BEFORE SCIM was enabled are NOT automatically provisioned, they show an indicator in the UI and need to be manually provisioned once. Critically: fully deactivating or unassigning a user in OKTA deactivates their SonarQube account, but merely suspending a user in OKTA leaves their SonarQube account unchanged, a genuinely easy-to-miss distinction. Unlike SAML, SCIM requires a direct, reachable network path from the IdP to SonarQube; if SonarQube isn't reachable from the public internet, an on-premises provisioning agent is required as a workaround, this is a real deployment blocker for customers with locked-down networks.

Grading notes

Pass: correctly distinguishes SCIM (push-based provisioning) from SAML (pull/redirect-based authentication), correctly reproduces the deactivate-vs-suspend distinction with an actual test, and names the stricter network-reachability requirement versus SAML. This is one of the highest-value items in the whole exercise for real support tickets.

19

Trigger code scanning alerts on GitHub

Difficulty 9/10Stretch

Goal: Understand GitHub Code Scanning integration, where SonarQube's security findings surface as native GitHub Security alerts.

Model answer

GitHub Code Scanning integration requires the repository already imported/connected to SonarQube, plus specific GitHub App permissions (Code scanning alerts: Read and write) and a subscription to the Code scanning alert event. Once configured, security vulnerabilities found by SonarQube analysis appear as native GitHub Code Scanning alerts under the repo's Security tab, in addition to SonarQube's own UI. Status changes sync bidirectionally: changing an alert's status in GitHub sends a webhook to SonarQube that updates the corresponding issue's status, and vice versa.

Grading notes

Pass: actually triggered a real vulnerability finding and confirmed it appeared in GitHub's Security tab, and tested the bidirectional sync in at least one direction, correctly identifying that it's webhook-driven rather than a simple one-time API push.

20

Block the merge of a PR when the Quality Gate fails (ADO, GitHub, etc.)

Difficulty 5/10Stretch

Goal: Understand DevOps-platform-native branch policies and PR checks, and how they enforce a SonarQube Quality Gate result.

Model answer

On Azure DevOps, this is a branch policy: add the SonarQube/Quality Gate status check under "require approval from additional services" and set it to Required (Optional would let users merge anyway despite a failing gate). On GitHub, this is a branch protection rule requiring the SonarQube status check to pass before merging. In both cases, the check has to have successfully reported at least once before it becomes selectable in the policy UI, if it's missing from the dropdown entirely, the most likely causes are an incomplete platform integration binding, a pipeline that's never actually run a PR analysis with decoration, or the check name not matching what the policy UI expects.

Grading notes

Pass: actually configured a Required (not just Optional) policy/rule and confirmed a failing Quality Gate genuinely blocked the merge button, and can name at least one plausible cause if the status check never appears as a selectable option, a very common real support scenario.

21

Set up SAML authentication using Keycloak

Difficulty 10/10Stretch

Goal: See a third SAML identity provider option. The catalog itself flags this as very optional, self-hosted Keycloak is useful for testing but isn't widely used by real customers, so weigh the time investment before diving in.

Model answer

Keycloak is a self-hosted, open-source identity provider; since it isn't a managed cloud service like OKTA or Azure AD, you first need to stand up your own Keycloak instance (a container image is the fastest path) before configuring anything. From there, the same SAML concepts apply: register a SAML client in Keycloak, configure matching settings in SonarQube, and test the login flow. The catalog itself explicitly flags this as low-value effort relative to the other SAML providers, since Keycloak isn't widely used by real customers, this is a reasonable one to skip or timebox strictly if OKTA and/or Azure AD are already done.

Grading notes

This is explicitly optional and low-priority per the source catalog. Pass (if attempted): got a real login round-trip working against a self-hosted Keycloak instance. Pass (if skipped): gave a brief, reasoned explanation for skipping (time tradeoff, already covered SAML fundamentals via OKTA/Azure AD) rather than leaving it blank with no context, that's the actual signal this item is testing for.
