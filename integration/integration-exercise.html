Create a PR on one of the DevOps platforms

Difficulty 1/10Core

Goal: Know the Git basics (clone/pull/push/commit) and how repos/branches work, before layering any SonarQube integration on top.

Where to look, not what to write
  • Pick any DevOps platform you have access to (GitHub, GitLab, Bitbucket, or Azure DevOps) and clone a test repo.
  • Create a branch, make a small commit, push it, and open a pull request against the main branch.
  • This is a prerequisite for nearly everything else in this exercise, if any of clone/branch/commit/push/PR felt unfamiliar, spend extra time here before moving on.

Set up a webhook (global or project level)

Difficulty 2/10Core

Goal: Understand how a SonarQube webhook is triggered and what information it can carry.

Where to look, not what to write
  • Find where webhooks are configured, either globally (Administration) or per-project, and point one at a URL you can inspect (a request-catching tool like webhook.site works well for testing).
  • Trigger an analysis and confirm the webhook actually fires, then inspect the payload it sent.
  • Look at what optional configuration exists for including more information in the payload (e.g. secret signing, custom properties), and think about what a receiving system would use this for (triggering a downstream deploy, posting to chat, etc.).

Set up a Quality Gate wait step on top of your pipeline

Difficulty 3/10Core

Goal: Understand how a pipeline waits for the Quality Gate result, and how to troubleshoot the most common failure mode: timeouts.

Where to look, not what to write
  • Using the pipeline you set up in the earlier item, add whatever step or task "waits for Quality Gate" in your CI tool (for example, a dedicated task/step, or a scanner flag depending on platform).
  • Confirm your pipeline actually pauses and reflects Pass/Fail based on the Quality Gate outcome.
  • Deliberately investigate the timeout scenario: what causes a wait-for-QG step to time out, and what would you check first if a customer reported this? (Hint: think about background task processing time and network reachability between CI and SonarQube.)

PR decoration for Azure DevOps

Difficulty 5/10CorePick one

Goal: Observe PR decoration working end to end on Azure DevOps, and know how to troubleshoot it via Compute Engine logs.

⚠ Pick one of these four, not all of them.

Where to look, not what to write
  • Set Compute Engine (CE) logging to INFO or DEBUG level and watch the logs while a PR analysis with decoration runs, so you can see exactly what SonarQube does during that step.
  • Understand Azure DevOps pipeline YAML syntax well enough to trigger a PR-triggered pipeline run, and know the difference between a "classic" (UI-designed) pipeline and an Infrastructure-as-Code (YAML) pipeline, this affects how you'd retrieve or troubleshoot the pipeline definition.
  • If you have a classic pipeline, find how to export/view its YAML representation, useful for support scenarios where a customer only has a classic pipeline to share.

Set up SSO header authentication

Difficulty 5/10Stretch

Goal: Understand HTTP header-based SSO, where SonarQube trusts headers set by an upstream proxy instead of handling login itself.

Where to look, not what to write
  • Find the SSO header authentication settings (login/name/email header names, and the enable flag).
  • Since a real reverse proxy is overkill for testing, use a browser extension that lets you inject custom request headers (a header-modifier extension) to simulate what a proxy would send.
  • Confirm you can "log in" purely by sending the right headers, and separately test what happens without them, do you get an error, a login prompt, or something else? Also note the version of the parameter set you used, since exact property names have shifted across SonarQube releases.

Set up SAML authentication using OKTA

Difficulty 5/10CorePick one

Goal: Understand the SAML protocol well enough to wire up a real identity provider, using OKTA as a free, accessible option.

⚠ At least one saml provider is a must, not all of them.

Where to look, not what to write
  • Sign up for a free OKTA developer/Integrator Free Plan instance: OKTA developer signup.
  • Create a SAML application in OKTA and configure SonarQube's SAML settings (IdP metadata/entity ID, SSO URL, certificate, attribute mappings) to match.
  • Test the login flow end to end, from clicking "Log in with SAML" through OKTA's authentication and back into SonarQube as a logged-in user. Note where a mismatch (wrong entity ID, wrong attribute name) would show up as an error, this is genuinely useful for future troubleshooting.

Set up Jenkins and scan a project with it

Difficulty 7/10Stretch

Goal: Understand Jenkins well enough to connect it to a DevOps platform and run a real scan, including Jenkins' own architecture.

Where to look, not what to write
  • Connect a Bitbucket or GitHub project to a Jenkins instance (a job that checks out the repo and runs a build).
  • Configure a SonarQube scanner step in that Jenkins job and confirm a successful analysis lands in SonarQube.
  • Extra mile: try scanning a C# or C++ project on Jenkins running on Windows, a genuinely different setup than a typical Linux/Java job. A public example repo exists for this if you want a ready-made target.
  • Along the way, get familiar with Jenkins pipeline vs. freestyle jobs, where Jenkins configuration lives (Java versions, secrets/credentials, executables, logs), and Jenkins' agent/master (now sometimes called controller/agent) architecture, all common sources of "why doesn't my Jenkins scan work" tickets.

Set up GitHub user/group provisioning

Difficulty 9/10Stretch

Goal: Understand automatic user and group provisioning from GitHub, including exactly when sync happens.

Where to look, not what to write
  • This requires GitHub authentication to already be set up (see that earlier item), provisioning builds on top of authentication, it doesn't replace it.
  • Enable GitHub provisioning and investigate which APIs it actually calls behind the scenes (organization membership, team membership).
  • Work out precisely what happens to a user and their group memberships once provisioning is enabled, especially for a user who already existed in SonarQube before provisioning was turned on, and what happens if a user or team is removed on the GitHub side.
  • Also determine when synchronization actually happens: is it real-time, on next login, or on some scheduled interval?

Set up SCIM provisioning on OKTA

Difficulty 9/10Stretch

Goal: Understand SCIM as a provisioning protocol, distinct from SAML authentication, including its stricter network requirements.

Where to look, not what to write
  • Using the OKTA instance from your SAML setup item, enable SCIM provisioning and connect it to SonarQube.
  • Work out what APIs SCIM actually uses, and what happens to a user or group that was assigned in OKTA BEFORE SCIM was enabled, versus one assigned after.
  • Deliberately test the deactivate vs. suspend distinction in OKTA: deactivate one test user and merely suspend another, then check what happened to each in SonarQube. This distinction is a genuine, well-documented gotcha.
  • Note the network requirement that makes SCIM different from SAML: SAML can tolerate SonarQube not being directly reachable from the IdP, but SCIM cannot, unless an on-premises provisioning agent is used. What would this mean for a customer whose SonarQube instance isn't reachable from the public internet?

Trigger code scanning alerts on GitHub

Difficulty 9/10Stretch

Goal: Understand GitHub Code Scanning integration, where SonarQube's security findings surface as native GitHub Security alerts.

Where to look, not what to write
  • This requires your GitHub repository to already be imported/connected to SonarQube.
  • Configure the GitHub App permissions needed for this (Code scanning alerts: Read and write, plus subscribing to the Code scanning alert event).
  • Run an analysis that produces at least one security vulnerability, and confirm it appears both in SonarQube's own UI and as a Code Scanning alert under GitHub's Security tab.
  • Test the bidirectional sync: change the alert's status in GitHub, then check whether that's reflected back in SonarQube (and vice versa), and understand this happens via a webhook GitHub sends to SonarQube.

Block the merge of a PR when the Quality Gate fails (ADO, GitHub, etc.)

Difficulty 5/10Stretch

Goal: Understand DevOps-platform-native branch policies and PR checks, and how they enforce a SonarQube Quality Gate result.

Where to look, not what to write
  • Prerequisite: you'll need a working pipeline and PR decoration already set up on whichever platform you choose (reuse an earlier item).
  • On Azure DevOps: find the branch policy for "require approval from additional services" / status checks, add the SonarQube/Quality Gate status, and set it to Required (not Optional). On GitHub: find the branch protection rule for required status checks and require the SonarQube check.
  • Deliberately fail the Quality Gate on a test PR and confirm the platform actually blocks the merge button, not just shows a warning.
  • If you can't get the status check to appear as an option at all, that's itself a real, common support scenario, note what you'd check first (global integration binding, pipeline configuration, whether the check has ever successfully reported once).

Set up SAML authentication using Keycloak

Difficulty 10/10Stretch

Goal: See a third SAML identity provider option. The catalog itself flags this as very optional, self-hosted Keycloak is useful for testing but isn't widely used by real customers, so weigh the time investment before diving in.

Where to look, not what to write
  • This is explicitly marked as low-priority in the source catalog, don't feel obligated to spend significant time here if you've already done OKTA and/or Azure AD.
  • If you do attempt it: Keycloak is self-hosted, so you'll need to stand up your own instance (a container image is the fastest path) before you can even begin configuring a SAML client.
  • Configure a SAML client in Keycloak and match SonarQube's SAML settings to it, then test the login flow the same way as your other SAML items.
  • If you skip this one, that's a reasonable call, note briefly why (time tradeoff) rather than leaving it blank with no context.
